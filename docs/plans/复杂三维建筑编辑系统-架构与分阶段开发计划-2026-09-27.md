# 复杂三维建筑编辑系统：架构与分阶段开发计划

日期：2026-09-27。状态：技术路线计划，尚未完成几何内核选型和真实工程性能验收。

本文件替代《建筑模型与立面剖面生成-开发计划》中关于“三维仅需体量、面排序即可消隐、无需第三方几何内核”的判断；原计划关于二维图纸提取、建筑参数复用、CAD 落图与图框排版的内容继续适用。实施前以本文件的试验门槛核准具体依赖、许可证及交付范围。

## 1. 目标与边界

目标是在独立的万落建筑模型程序中编辑具有建筑语义的三维模型，并从同一模型生成可更新的 CAD 平面、立面、剖面及大样。墙、板、柱、梁、门窗、楼梯、屋面等必须能保持稳定身份、参数、层级和相互依赖；用户可以在平面或三维中修改它们，并通过撤销/重做恢复。第一批复杂编辑以斜墙、曲墙、异形板、墙洞与交接、楼梯、坡屋面、构件布尔切割和局部节点为验收对象。自由曲面雕刻、动画、实时照片级渲染不作为首批交付目标。

Unity/Unreal 是强大的游戏/实时内容引擎，并非“简单引擎”；问题是它们不能自动提供建筑参数关系、精确 B-rep 几何、可靠布尔、工程制图和 CAD 更新。HelixToolkit/OpenTK 同样只解决视口及部分交互基础，不能充当建模内核。Blender 的可借鉴处是将可编辑模型、依赖更新、GPU 视口与最终渲染分开；Blender 的网格编辑路线也不等同于工程精度的 B-rep。IfcOpenShell 的 Bonsai 展示了 Blender 内做 IFC 建筑编辑的另一产品路径，可以参考工作流，但本计划不把 Blender 源码或插件直接嵌入现有 .NET 程序。

## 2. 仓库现状与需要替换的假设

| 现有资产 | 可保留 | 复杂编辑前的缺口 |
| --- | --- | --- |
| `Shared/BuildingModel/ModelTypes.cs` | 毫米、双精度、楼层/墙/洞口等建筑语义及部分稳定 ID | 当前对象种类与约束有限；几何数据和模型身份需分层，增加类型版本与迁移 |
| `BuildingVolumeBuilder`、`VolumeRenderer`、`VolumeCanvas` | 小模型原型和回退预览 | 输出的是显示面，非可编辑精确实体；CPU 消隐随面数增长变慢 |
| `ModelEditHistory` | 小模型现有撤销行为可作兼容基线 | 64 份完整 JSON 快照随模型增长成本高；缺少跨构件事务和差量变更 |
| `OrthographicProjector`、`ViewDocument` | 现有二维规则、图层与视图格式 | 自研消隐需几何正确性基准；复杂曲面/布尔后的立剖面不能靠显示面推断 |
| `BuildingModelCadBridge` | CAD 读取与二维落图入口 | 需登记视图放置实例、版本与受控更新，保留人工补绘 |
| 门窗/楼梯/制图标准/项目管理 | 可复用参数和应用外壳 | 楼梯与现有生成器的映射仍需补齐；模型文件保存和云同步须做并发版本控制 |

上一轮本机合成基准只测 `VolumeRenderer.Project`：276 面约 7 ms，2208 面约 86 ms，不含绘制。它证明当前路径不适合持续扩大面数，不证明引入某个 GPU 控件后所有编辑都会变快。

## 3. 目标架构与数据契约

```text
CAD 图纸导入 / 构件化输入 / 三维编辑命令
                    ↓
建筑语义模型（唯一权威：构件 ID、参数、宿主关系、楼层、材料、版本）
                    ↓ 有向依赖图与事务：只标记受影响构件
几何服务（准确 B-rep、布尔、截面、有效性检查；可替换实现）
                    ├─ 三角网格缓存 → GPU 视口、拾取、临时操纵柄
                    └─ 精确截面/轮廓 → 制图规则 → ViewDocument → CAD 受控更新
```

1. **语义模型是文件权威**：继续使用建筑对象参数，不把渲染三角形或内核的临时指针当主文件。为构件、视图、CAD 放置实例分别分配稳定 ID；记录模型 schema、修订号、单位、坐标系、来源和外部参数版本。旧 `model.json` 必须可迁移并能无损回退备份。
2. **几何内核是计算服务**：提供 `BuildShape(element)`、`Cut/Open/Union`、`IntersectSection`、`ProjectHiddenLines`、`ValidateShape`、`Tessellate` 等窄接口；内核返回附带构件 ID 和拓扑映射的结果。内核失效时报告具体构件，不保存不完整的正式视图。
3. **视口是派生缓存**：网格按构件和楼层分块，GPU 用深度缓冲处理交互遮挡；只把修改构件及其依赖项重新网格化。相机转动不重新做布尔/生成网格。拾取结果须映射回构件 ID，面/边级选择保留拓扑引用及失效检测。
4. **图纸是独立派生物**：CAD 线稿由精确几何和建筑制图规则生成，不取屏幕截图。`ViewDocument` 增加来源构件、模型修订和视图版本。标注、人工补绘按归属保留，自动生成部分可整批更新。
5. **编辑以命令事务提交**：命令先校验约束，生成不可变输入快照；成功后一次提交模型、依赖索引和历史记录，失败时全部回滚。大模型撤销使用差量/反向命令与定期检查点，而不是每步复制整栋 JSON。

## 4. 内核与视口选型：先对照试验，再锁定

| 层 | 首选试验 | 对照/退路 | 是否已经确定 |
| --- | --- | --- | --- |
| 精确几何 | OCCT 原生 C++：B-rep、布尔、截面、精确隐藏线、三角化；用小而稳定的 C ABI 连接 .NET，边界不泄漏 `TopoDS_Shape` | 在已限定的简单构件继续用自研几何；若 OCCT 代价或结果不满足要求，再评估其他商用/开源内核 | **未确定**，必须通过第 5 节试验。OCCT 是能力候选，不是现成建筑语义系统 |
| 实时视口 | HelixToolkit.Wpf.SharpDX v3 试验页，WinForms `ElementHost` 承载 | OpenTK GLControl：宿主简单但拾取、材质、操纵柄需自建；现有 CPU 预览作降级路径 | **未确定**。已仅验证 Helix 包可还原、视口可构造，未测真实模型、显卡及 DPI |
| IFC 互通 | 语义模型稳定后评估 IfcOpenShell 导入/导出 | 首批只保留现有项目格式和 CAD 交换 | **后置**；IFC 不是编辑内核。许可与依赖逐模块核验 |

OCCT 官方文档列有 B-rep 布尔 `Cut/Fuse/Common/Section/Splitter`，也区分精确与多边形隐藏线；它适合充当几何计算候选。`HelixToolkit` 提供视口与命中测试基础，但不能替代 OCCT 的精确几何。原生交互先做最小探针：同一构件能建 B-rep、切窗洞、转成带构件 ID 的网格、导出剖切线，再送入 .NET 视口。使用 OCCT/IfcOpenShell 前由项目负责人核对实际分发方式与许可证义务，不把本计划当法律结论。

## 5. 四项选型试验（未通过不得大规模迁移）

1. **几何正确性**：同一批固定样例覆盖 200 mm 墙中线偏移剖切、T/L/十字墙接头、临界相切、斜墙、曲墙、重叠洞口、薄板、楼梯与坡屋面。检查实体闭合/有效性、开洞、截面数量和容差；与人工标注的基准 DWG 比较，不能以“看起来差不多”通过。
2. **编辑链路**：选一堵有门窗的墙，拉端点、改厚度、改洞口尺寸、跨楼层复制，然后撤销/重做。墙体、洞口、关联标注和 CAD 视图来源 ID 必须一致；无效操作可回滚且不会损坏工程。
3. **性能**：用同一真实项目、同一显卡和 1000/10000/50000 构件的合成场景测首次打开、首帧、旋转 P95 帧耗时、单构件编辑至画面稳定 P95、视图生成时间、内存/显存峰值。30 FPS 交互的目标为旋转 P95 < 33 ms；单构件编辑目标 P95 < 200 ms。数字是验收目标，须记录机器配置和模型复杂度，不是当前性能声明。
4. **部署兼容**：在 Windows 100%/150%/200% 缩放、跨屏、核显/独显、远程桌面和显卡初始化失败场景测试。WinForms/WPF 事件与焦点、CAD R24/R25、.NET 发布包、无管理员权限安装均需验收；失败时可以回到旧预览并保留工程。

试验决策：几何正确性优先于速度；若 OCCT 通过但 UI 桥接慢，优化网格缓存/批处理而不丢弃精确内核；若 Helix 失败但内核通过，改试 OpenTK，语义和几何服务保持不变。记录每条路线的二进制体积、第三方依赖、许可审查和维护成本。

## 6. 实施阶段、交付物与通过条件

以下周期是 **2 名熟悉仓库的开发人员的粗估**，在选型试验后重估；阶段可以并行设计，正式发布按验收顺序推进。

| 阶段 | 粗估 | 主要工作 | 通过条件 |
| --- | --- | --- | --- |
| G0：基线与样例 | 2–3 周 | 锁定 3 个真实项目、可公开的脱敏模型、几何金样、性能脚本、旧模型备份；复核保存失败阻断发布及墙厚偏移剖切的现有修复，并补齐 CAD 重复落图的受控更新 | 旧测试全绿；失败不改正式文件；三次更新无重影 |
| G1：技术试验 | 3–5 周 | OCCT C++ 桥接与 Helix/OpenTK 视口各做最小端到端样例；测第 5 节四项；完成许可证/发布包检查 | 书面选择内核与视口；若关键样例不通过，缩小范围或更换候选，不继续堆 UI |
| G2：模型与事务 | 5–8 周 | schema v2、旧文件迁移、稳定 ID、宿主关系、依赖图、编辑命令、差量撤销、跨进程修订冲突 | 旧项目可打开/回退；1000 构件连续编辑/撤销无身份错乱；并发保存不覆盖 |
| G3：精确构件 | 8–14 周 | 墙/板/柱/梁、门窗开洞、交接、斜/曲墙、楼梯及屋面映射；有效性检查与局部重建 | 第 5 节几何金样通过；编辑只使受影响对象失效；错误构件可定位 |
| G4：三维交互 | 6–10 周 | GPU 场景、分块缓存、构件/面/边拾取、吸附、操纵柄、楼层隔离、剖切、操作预览/提交 | 真实项目旋转和编辑达到记录的性能门槛；跨屏/DPI、显卡回退通过 |
| G5：立剖面与 CAD 同步 | 6–10 周 | 从精确几何抽截面/轮廓、制图规则、版本化视图、CAD 放置实例登记与事务更新 | 四面立面、每层平面剖切、指定剖面均可重算；人工补绘保留；一次撤销恢复 |
| G6：试点与扩展 | 按项目 | 三个真实工程验收、缺陷闭环，再排异形节点、族库/参数模板、IFC 交换等 | 交付图纸人工复核通过，性能与崩溃数据稳定，才宣布复杂三维编辑可用 |

每阶段完成后都保留可运行版本。先让一堵墙的编辑、开洞、截面、CAD 更新闭环正确，再扩大构件种类。不要同时迁移 UI、模型格式和几何内核后才第一次集成。

## 7. 并行工作包与工程规则

- **模型/几何**：领域对象、约束、OCCT 桥、拓扑稳定性与金样。拓扑面号在布尔后可能变化；工程身份绑定到语义构件/特征，不靠内核瞬时面序号。
- **视口/交互**：渲染、选择、吸附、手柄、预览、缩放与 DPI。UI 线程只做交互和提交；几何后台计算基于不可变修订快照，旧任务结果按修订丢弃。
- **图纸/CAD**：视图源对象登记、制图样式、实例更新、标注保护和 DWG 对照；CAD 数据库操作继续在宿主受控事务内。
- **数据/发布**：schema 迁移、原子保存、修订冲突、崩溃恢复、云同步与原生 DLL 打包。每个第三方依赖有版本、来源、许可、哈希和兼容测试记录。

关键回归集必须包含单位/坐标、容差、退化几何、用户中断、文件写入故障、原生调用异常、显卡恢复和旧模型往返。对外发布不以自检通过代替 AutoCAD 真机和真实工程人工核对。

- [HelixToolkit 视口命中测试](https://helix-toolkit.github.io/helix-toolkit/develop3/api/HelixToolkit.SharpDX.IViewportExtensions.html)、[IfcOpenShell 仓库](https://github.com/IfcOpenShell/IfcOpenShell)：分别支持视口和 IFC 候选范围；项目适配、性能及许可仍按试验核实。

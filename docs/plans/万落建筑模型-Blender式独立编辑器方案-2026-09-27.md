# 万落建筑模型：借鉴 Blender 的独立编辑器方案

日期：2026-09-27。决定：**保留万落独立程序，以 Windows、macOS、Linux 桌面兼容为架构目标**，参考 Blender 的工作区和交互，不嵌入或复制 Blender 的界面代码。本文细化《复杂三维建筑编辑系统：架构与分阶段开发计划》的 UI 路线；几何内核和 CAD 图纸权威关系仍按原计划验证。移动端与浏览器不在首批目标内。

## 为什么不能直接拿 Blender UI 当控件

Blender 的编辑区、事件循环、绘制和视口是一套紧密耦合的应用架构；布局脚本虽有 Python 部分，绘制及交互核心在 C/C++，不是可直接置入 WPF 的独立 UI 组件。直接移植源码会变成维护 Blender 分支，并引入许可证、升级和 CAD 集成成本。万落要借鉴的是**工作区组织与操作原则**，不是像素级照搬或换一个皮肤。

## 工作区信息架构

```text
标题 / 文件 / 撤销重做 / 保存状态 / CAD 连接状态
工作区页签：建筑建模 | 平面编辑 | 立面剖面 | 图纸发布
工具栏：选择、墙、板、门窗、楼梯、屋面、剖切、测量
┌───────────────┬─────────────────────────────────┬────────────────────┐
│ 项目/楼层/构件树 │ 主视口：三维、平面、立面或剖面       │ 属性：当前构件参数     │
│ 搜索、显隐、锁定 │ 选择、吸附、操纵柄、局部隔离         │ 宿主关系、约束、材料   │
│ 与视口双向联动   │ 视图导航、剖切面、图纸预览           │ 修改预览与校验消息     │
└───────────────┴─────────────────────────────────┴────────────────────┘
底部：命令历史 / 校验与后台任务 / 坐标、单位、性能状态
```

- 各区可拖动分隔、折叠、保存工作区布局；首次打开采用经过测试的默认比例。小屏幕自动收起左/右辅助区，让主视口保持最低可操作尺寸，避免整个窗口出现双层滚动条。
- 左侧树按“项目→楼层→构件类型→构件”组织。树、视口、属性区共享同一选择状态；单选、多选、隐藏、锁定都使用稳定构件 ID，不能用网格序号或列表行号。
- 右侧属性区按对象类型显示可编辑参数。修改分为拖动预览与提交两阶段；提交前检查宿主、约束和几何有效性。错误定位到构件，不能静默生成残缺图纸。
- 主视口保留建筑软件习惯：毫米单位、正交平立剖、楼层标高、轴线、墙线、图层/显示样式和精确吸附；参考 Blender 的视图导航、对象树和上下文属性，但不让用户为了画墙先学习通用网格建模。
- CAD 返回采用明确的“生成/更新视图”命令，显示模型修订与 DWG 放置实例。三维视口只是显示缓存，不能以屏幕投影替代正式立剖面线稿。

## 技术边界与实现次序

1. **共享数据与命令层先于外观**：现有 `Shared/BuildingModel` 中的语义模型继续作为文件权威；先抽出 `SelectionService`、`EditCommand`、`Undo/Redo`、`ViewportScene`、`DocumentRevision` 等窄接口，让 UI 能换而不重写模型/CAD 逻辑。核心工程使用跨平台 .NET 目标框架，移出 `System.Windows.Forms`、注册表、Windows 路径、AutoCAD 程序集等平台依赖。现有 WinForms 建模程序保留为 Windows 可运行基线。
2. **跨平台 UI 首选试验 Avalonia**：项目目前以 C# 为主，Avalonia 可复用领域层；窗口、停靠区、构件树、属性面板、DPI/主题先做最小工作区。GPU 视口另做 `OpenGlControlBase` 或同等可维护宿主探针，不把跨平台 UI 支持误认为复杂三维视口已解决。Qt 6/C++ 是对照路线：原生视口整合更直接，但需要跨语言桥或迁移大量现有 C# 代码，并核算 Qt 组件许可证与发布成本。
3. **WPF/Helix 试验止于技术记录**：WPF 不支持 macOS/Linux，不应作为最终主程序；当前 HelixToolkit.Wpf.SharpDX 试验只能启动并加载网格，真实窗口的 3D 内容仍未正常显示，故不得作为跨平台路线基础或发布版本。
4. **视口候选比较**：以同一墙窗模型、相机与构件 ID，在 Avalonia GPU 控件和 Qt 6 原生视口各做可运行探针。必须先在 Windows 与至少一台 macOS、Linux 机器上可见、可拾取、可旋转，再测 1000/10000/50000 构件、DPI/跨屏及显卡失效。若 Avalonia 的视口焦点、覆盖层或帧时间不达标，选择 Qt/C++ 前端；领域模型与文件契约保持独立。
5. **CAD 是平台适配层**：现有 AutoCAD Managed .NET 插件继续只在 Windows 宿主运行。跨平台编辑器通过版本化模型/视图文件与它交换，不在领域层引用 AutoCAD DLL；macOS/Linux 先支持模型编辑和中立格式导出。其他平台直接向 AutoCAD 写 DWG 的能力，须另选当地可用 API 并验证，不能承诺现有插件原样移植。
6. **先做一条可编辑闭环**：选墙→改长度和洞口→预览→提交→撤销/重做→重算立剖面→在 Windows 更新 DWG。闭环通过后扩展板、楼梯、屋面和复杂布尔。不要先把所有 WinForms 页面外观重做一遍。
7. **避免主线程卡顿**：模型修订驱动增量重建；相机转动只用已有 GPU 网格。耗时几何在后台按不可变快照计算，旧修订结果丢弃；UI 线程只处理输入、选择和提交。记录首帧、旋转 P95、单构件编辑 P95、内存与显存，目标沿用主计划第 5 节。

## Blender 几何能力能否作为内核

可做**候选试验**，但不能把 Blender 的 BMesh/修改器等同于独立、工程精确的 CAD 内核。BMesh 是面向多边形拓扑局部编辑的数据结构；Blender 的布尔修改器有 `Exact` 求解选项，此处“Exact”指该网格布尔算法的求解模式，不自动保证精确 B-rep 曲线、拓扑持久命名或符合 CAD 出图公差。Blender `Mesh` 位置以 `float3` 存储，毫米级大坐标与多次转换必须实测误差。

技术上能用 Blender 后台进程或 `bpy` Python 模块处理模型：万落独立 UI 将语义构件及单位/坐标传给常驻 Blender 工作进程，取回网格、构件映射、剖切结果或渲染产物。Blender 官方提供后台脚本和 `bpy` 模块方式，但这不是从 .NET 直接链接的稳定 C ABI。进程边界、依赖打包、版本锁定、许可证和故障恢复都要由我们负责。本机 Blender 4.5.3 LTS 的一次空后台启动约 2.3 秒，因此绝不能为每次鼠标拖动新开进程；须测常驻进程的往返延迟。

G1 增加 Blender/OCCT 同题对照：同一堵墙开窗后做墙厚、窗位、相切/重叠洞口、斜/曲墙、剖切及隐藏线；对照毫米误差、实体有效性、构件/面身份、撤销重做后的可重复性、单构件编辑 P95 与进程故障恢复。若 Blender 通过工程精度与性能门槛，可考虑承担更多几何任务；若只通过网格/可视化门槛，则将其限定为可选的网格处理或渲染服务，正式 CAD 立剖面仍走精确几何服务。**在对照试验前不宣称某一个已是最终内核。**

首轮直墙单窗探针已落地并运行，结果和未覆盖范围见[《建筑模型 G1：Blender 首轮几何探针》](../reviews/建筑模型G1-Blender首轮几何探针-2026-09-27.md)。

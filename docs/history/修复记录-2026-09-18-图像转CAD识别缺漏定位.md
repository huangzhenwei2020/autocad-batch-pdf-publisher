# 修复记录 2026-09-18：图像转 CAD 识别缺漏的定位与修复

## 起因

用户反馈「图像转 CAD 的功能有很多地方没有识别到」。这条链路原本没有任何量化手段，
好坏只能靠肉眼看结果，所以先做了一个能出数字的诊断工具，再按数字定位问题。

## 诊断工具

`LineVisionDiagnostics/`（独立工程，不参与发布构建）＋ `build/Measure-LineVision.ps1`。

工具把同一张图分别跑两条识别路径，输出可对比的指标：

- **覆盖率**：墨迹像素中，落在某条已识别线 2px 邻域内的比例——衡量「漏了多少」
- **<10px 碎线数**：长度不足 10px 的段数——衡量「碎不碎」
- **端点悬空数**：端点 3px 内没有接续的端点数
- **分阶段掩膜对比**：内核的二值化掩膜 vs 主程序的掩膜，以及骨架掩膜，用来判定
  墨迹是在二值化、细化、还是追踪哪一步丢的

用法：

```powershell
# 编译内核并部署到 dist，然后测量
build\Measure-LineVision.ps1 -Image <图片路径> [-Region x,y,w,h]
# 只看指标不动内核
LineVisionDiagnostics\bin\Release\net8.0-windows\LineVisionDiagnostics.exe --image <图> --help
```

## 定位到的四个缺陷

### 1. 界面参数根本没传给矢量内核（最主要）

`LineVisionForm.cs` 在矢量模式下会丢掉主算法结果：

```csharp
result.Polylines = vector.Polylines; result.WallRegions = vector.WallRegions;
result.Segments.Clear();
```

而 `LineVisionVectorWorkerClient` 起内核时只传了 `--threshold --wall-min --wall-max`，
`最短线`／`补断线`／`共线容差`／`横竖吸附`／`识别斜线` 一个都没传，内核里也是硬编码。
**结论：面板上这些参数对最终结果毫无影响。**

### 2. 矢量内核的启用逻辑自相矛盾

模式按 `Outline ? "outline" : (Hybrid || DetectWallFills) ? "hybrid" : ...` 计算，
而「识别墙体填充」默认勾选，于是模式恒为 `hybrid`，VTracer 每次都会跑；
但 `Outlines` 的 `enabled` 只在显式选「保留轮廓」时才为真。
**结论：默认配置下 VTracer 白跑一遍然后被丢弃。**

### 3. `AddPath` 里写死了 4px 长度门槛

短于 4px 的路径直接丢弃，界面上把「最短线」调到 0 也保不住。
**结论：尺寸起止线、窗棂这类真实短构件被静默吃掉。**

### 4. `Trace` 只给每个起始像素一次机会

原实现先只从「度数≠2」的像素出发走一次。一个交叉点有 3 条以上分支，
第一条路径走到它就把边标记为已访问，**这个交叉点剩下的分支再也没人走**。

用掩膜分阶段比对证实：追踪出的折线只覆盖骨架的 **88.9%**。

## 已做的修复

| 文件 | 改动 |
| --- | --- |
| `LineVisionVectorWorkerClient.cs` | 把 `最短线`／`补断线`／`共线容差` 真正传给内核 |
| `Program.cs`（内核） | 解析 `--minimum`／`--merge-gap`／`--collinear`，新增 `--dump-mask` 用于诊断 |
| `SkeletonVectorizer.cs` | 新增 `CleanAndMerge`：按拐角切分 → 合并共线 → 按长度筛 |
| 同上 | 合并按（方向、法向位置）分桶，避免 O(n²)：**45.6s → 1.5s** |
| 同上 | `Trace` 改为遍历「每个像素的每条边」，不再漏走交叉点分支 |
| 同上 | 去掉 `AddPath` 写死的 4px 门槛，交给 `--minimum` 决定 |
| `build/Measure-LineVision.ps1` | 编译→校验→部署→测量的辅助脚本 |

**顺序很关键**：必须「先合并、再按长度筛」。骨架路径是交叉点到交叉点的一段，
一条长墙会被与它相交的每条线切成许多短路径；先筛长度会把整堵墙当碎渣丢掉
（实测最短线 18 时覆盖率从 77.9% 掉到 56.3%）。

## 尚未解决

### 覆盖率仍低于旧算法

骨架 78.5%（最短线 0）vs 旧算法 86.3%。分阶段比对显示：

- **二值化不是主因**：内核墨迹 142,060 与主程序 147,283 完全重合，多余噪点为 0
- **主因在追踪之后的短残端**：±2px 窗口下仍差 5.6%，多为极短笔画残端

骨架法天然的代价是：一条 3px 宽的线，中心线只有 1px，覆盖率按「落在线上」计，
本就吃亏。这一点需要用户用真实图纸确认哪个更可用。

### 骨架输出的形态不适合直接当线稿

合并只减少了几十条（3,837 → 3,797），说明输出主体**不是共线碎片，而是围绕笔画
两侧的平行双轮廓**——这是骨架法的本质。要得到单线线稿，仍需要额外的处理。

### 「最短线」默认值 18 偏大

在骨架路径下 18 会把覆盖率压到 53%。旧算法下 18 也让覆盖率从 86.3% 掉到 77.5%
（换来碎线段从 477 降到 0）。默认值需要按目标形态重新定。

### 圆/弧在矢量模式下被丢弃

状态栏会报「圆弧 6 段」，但 `Segments.Clear()` 之后 `result.Arcs`／`result.Circles`
再没有机会被写入（`LineVisionCadWriter` 本身是支持写圆和弧的）。

## 一个教训：编译失败伪装成成功

改内核时加 `--dump-mask` 用了 `Directory`／`Path` 却忘了 `using System.IO`，
MSBuild 每次都报错，但我的过滤条件只匹配了 `已成功` 之类字样，没匹配 `error CS`，
于是**连续几轮都在测旧 exe**，得出过一组完全错误的数字（包括一个 45 秒的耗时）。
现在 `build/Measure-LineVision.ps1` 强制校验：编译有 error 就停、产物里必须能查到
新参数才部署。另外校验二进制里的字符串要注意：.NET 的字符串字面量是 UTF-16，
按 ASCII 读会误判为缺失。

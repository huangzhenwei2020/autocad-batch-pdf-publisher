# 建筑模型与立面/剖面生成 —— 开发计划（v1 草案）

> **一句话**：把用户已经画好的二维建筑平面图，变成一份**轻量、可编辑的建筑模型**，
> 再由模型自动投影生成立面图与剖面大样，并复用它已经配置好的制图标准、门窗参数、
> 楼梯参数、大样排版与项目管理。

- **草案日期**：2026-09-22
- **状态**：待评审（末尾有 9 个需要拍板的问题）
- **相关调研**：[商业 CAD 方案调研](调研-商业CAD三维建模与立面剖面方案.md)、
  [开源与学术调研](调研-2D平面图到3D建筑模型与立面剖面投影.md)、
  [AutoCAD 三维→二维投影 API 查证](调研-AutoCAD三维到二维投影API.md)
- **已核实的宿主能力**：**本机实测**——AutoCAD 2024（R24）`C:\Program Files\Autodesk\AutoCAD 2024\acdbmgd.dll`
  与 AutoCAD.NET 25.0.0（R25）NuGet 包 `autocad.net.model\25.0.0\lib\net8.0\AcDbMgd.dll`
  都含 `Section` / `SectionSettings` / `SectionType` / `SectionGeometry` / `GenerateSectionGeometry`；
  枚举值由程序集反射枚举得到（不是查文档推断）。复核方法见 §5.1 末。

## 1. 结论先行

1. **值得做，而且我们有别人没有的起点**：市面上"AutoCAD 插件式建筑建模 + 立面剖面"几乎没有开源实现（调研结论），
   而我们已经攒下了这套东西最难替换的部分——**制图标准（图层/线型/线宽/文字/标注样式/比例）、
   门窗参数（宽高/窗台高/分格/开启/框料/凸窗深度/材料/图集）、楼梯参数（层高/跑数/踏步/平台/楼板/梁）、
   大样排版引擎、图框登记、项目与云同步**。这些正是"生成一张能直接交付的立面图"需要的全部下游能力。
2. **不要自研几何内核，也不要在 v1 引入第三方内核**：宿主 AutoCAD 自己就有
   `Section` 对象与 `GenerateSectionGeometry`，能输出**已经分好类**的投影几何
   （剖切边界、剖切填充、背景、前景、曲面切线），并且 `SectionSettings` 允许
   **逐类指定图层 / 线型 / 线宽 / 颜色 / 填充图案 / 是否隐藏线**——这几乎是我们制图标准的一一对应。
   第三方内核（OCCT 的 HLRBRep）留作"任意方向剖切 + 精确隐藏线"的备选，不进 v1 依赖。
3. **v1 的定位必须是"半自动 + 问题清单"**，不是"点一下自动出全套施工图"。
   二维图纸转三维在墙体交接、洞口归属、层高推断上天生有歧义，行业里所有工具都靠
   "识别 + 人工确认"。我们要做的是：**把 80% 的重复劳动自动化，剩下的 20% 用一张清单明确交给用户**，
   并且**用户改完能一键重算**。
4. **复用优先级**：门窗参数 > 楼梯参数 > 制图标准 > 大样排版/图框 > 房间（天正房间对象）。
   其中门窗与楼梯参数是"一个字段都不用重填"的真复用，立面的门窗分格与楼梯剖面可以**直接调用现有生成器**。

## 2. 行业里别人怎么做（调研摘要）

### 2.1 中文生态：天正的"三维组合 + 立面/剖面生成"（有官方文档确证）

天正官方教材直接写明了这条链路的本质，等于替我们验证了技术路线：

> *"立剖面表现的是建筑三维模型的一个投影视图……**天正立面图形是通过平面图构件中的三维信息进行消隐获得的纯粹二维图形**，
> 除了符号与尺寸标注对象以及门窗阳台图块是天正自定义对象外，其他图形构成元素都是 AutoCAD 的基本对象。"*
> —— [天正建筑绘制立面图](https://chaoshi.zjtcn.com/classifydetails/1286714.html)、[绘制剖面图](https://chaoshi.zjtcn.com/classifydetails/1286742.html)

命令级流程（三步，与我们 §4.2 的设计几乎一致）：
**工程管理 → 楼层表（填各层"层高/文件"）→ 三维组合建筑模型 → `GJLM` 生成立面 / `GJPM` 生成剖面 → 修改深化 → 标注 → 填充**
（[三维组合步骤](https://www.hxsd.tv/wenda/299/)、[GJLM/GJPM 用法](https://yunzhi.zjtcn.com/3683179.html)）

**但它有一个硬约束，这条必须刻进我们的方案**：
*"其中各种构建必须是天正的构件——墙、柱、楼梯、阳台、坡道、屋顶等等，普通 cad 画的图是不行的"*，
用纯 CAD 平面图**无法**生成立面（[出处 1](https://yunzhi.zjtcn.com/39810628.html)、[出处 2](https://yunzhi.zjtcn.com/4605098.html)）。

由此得出我们方案里两个不可回避的设计点：

1. **"构件化绘制"应当成为一条正式的输入通道**，而不是只做"反推"。
   既然连天正都拒绝解析任意多段线，我们就不该把宝全压在"从双线墙里猜墙"上。
   我们可以提供一套自己的轻量构件命令（画墙带厚度/高度、放门窗直接取自现有门窗参数库、
   布置柱子/楼梯），**用户画的就是模型**——这条路的识别率接近 100%，
   而反推路线只用来兼容"已经画好的老图"。
2. **楼层表是唯一竖向数据源**（层高/标高/标准层），立面剖面只读它，不猜。

> 结论：**双通道输入**——① 构件化绘制（推荐、可靠）；② 从已有图纸反推（兼容老图，半自动 + 问题清单）。
> 门窗参数与楼梯参数两条通道都能复用（§3）。

### 2.2 国际商业：ACA / BricsCAD BIM / Revit / ArchiCAD

- **AutoCAD Architecture（ACA）**：AEC 对象在图形里就是三维实体，门窗通过**锚定**挂到墙上并自动开洞；
  立面/剖面的做法是"**画立面线 → 选对象集 → 生成二维剖面/立面对象**"，**隐藏线已删除**，
  外观由"二维剖面/立面样式 + 显示集"控制，生成后**与模型关联、可更新**。
  → [创建二维/三维立面的步骤](https://help.autodesk.com/cloudhelp/2024/CHS/AutoCAD-Architecture/files/GUID-074C9A40-4F35-4638-BBF1-282DC68F53EE.htm)、
  [About Elevations](https://help.autodesk.com/cloudhelp/2023/ENU/AutoCAD-Architecture/files/GUID-76879DE6-874B-4348-8E96-AE1D35786D5E.htm)。
  这是与我们**同生态、最贴近**的参照：可照搬"立面线 + 选择集 + 样式 + 可更新"，代价是我们没有 AEC 内核。
- **BricsCAD BIM**（**此处修正我先前的说法**）：其 `BIMIFY` 的输入是 **3D 实体，不是二维线**——
  *"BIMIFY analyzes a model and automatically classifies **3D solids** to building elements…"*，
  最后一步才是 "Create sections: Creates an elevation view and a plan section per floor"。
  **"2D 线自动识别成墙"的公开算法说明未找到确证**。
  → [Using Bimify（官方帮助）](https://help.bricsys.com/en-us/document/bricscad-bim/design-assistance/using-bimify)。
  启示：它是"先有体、再反推语义"，方向与天正/ACA 相反；我们走"对象自带语义"可以跳过最不可靠的"分类"环节，
  但它的产出清单（**每层一张剖切 + 四面立面**）可以直接作为我们的验收清单。
- **Revit**：靠**视图范围**（俯视图 / 剖切面 / 仰视图 + 视图深度）规则化"一个模型 → 不同表达"：
  与剖切面相交的构件用**剖面线宽**、低于剖切面的用**投影线宽**、视图深度内的用 `<超出>` 线型；
  剖面视图的宽度与深度由**裁剪区域**控制。
  → [关于视图范围](https://help.autodesk.com/cloudhelp/2016/CHS/Revit-DocumentPresent/files/GUID-58711292-AB78-4C8F-BAA1-0855DDB518BF.htm)、
  [剖面视图的宽度和深度](https://help.autodesk.com/cloudhelp/2024/CHS/Revit-DocumentPresent/files/GUID-16FF4EBC-66F0-498E-85F6-DA3274608710.htm)。
  **这一条直接塑造我们的图层表**（剖到/投影/超出三类线，见 §5.5）。
- **ArchiCAD**：*"Elevations generally do not 'slice through' the structure, but rather create a cross-section view
  of the structure from a distant point"*；立面线只是屏幕标记；Section/Elevation 视图有 **Model / Drawing 状态**
  决定更新方式。→ [ARCHICAD Help – Elevations](https://help.graphisoft.com/AC/23/INT/_AC23_Help/050_ViewsVB/050_ViewsVB-46.htm)。
  启示：**"立面的剖切面在建筑之外"**（我们 §5.1 的做法）正是成熟产品的做法；
  而且视图要有"**模型态/图纸态**"的概念（模型变了要不要自动重算、标注要不要保留）。
- **中文生态其它**：**广联达数维设计**官方口径是"三维设计为主、多视图联动保证图模一致，
  而**附属元素和注释走二维辅助设计**"（[出处](https://www.glodon.com/news/1146.html)）——
  与我们"**投影参数化、标注不参数化**"的设计完全一致；中望建筑有"自动创建立剖面"，浩辰建筑有楼层框/标准层。
  头部产品里**没有一家宣称"二维图纸全自动出图"**。

### 2.3 开源与可复用件（许可证已逐项核实）

| 方向 | 可用件 | 结论 |
|---|---|---|
| BIM 内核 | FreeCAD/IfcOpenShell（Python/LGPL）、xBim（C#/CDDL，允许闭源商用）、GeometryGymIFC（C#/MIT） | **都不进 v1**。没有能以 .NET 库直接嵌进插件的开源 BIM 内核；将来若要 IFC，用 xBim 或 GeometryGymIFC |
| 投影内核 | OCCT `HLRBRep`（LGPL-2.1 + 例外，可动态链接闭源商用） | **备选**，只在原生 Section 不够用时评估 |
| 平面图→3D | Raster-to-Vector（MIT）、CubiCasa5K（CC BY-NC，**禁商用**）、DeepFloorplan（GPL-3.0） | 我们的输入是矢量线而不是栅格图，**整节跳过**；只借鉴 R2V 的"平行线配对"思路 |
| DWG/DXF | ezdxf（MIT，但纯 Python，且**没有 3D 引擎**）、libdxfrw（GPL，排除）、ODA SDK（$3000 首年仅 100 份分发） | **DWG 全走宿主 API**，不引入 ODA |
| 立面展开 | `hueflow-elev`（AutoCAD LISP，MIT，四面墙立面展开） | 与需求最贴近，**读它的展开逻辑** |
| CAD 基础设施 | `AutoCADCodePack`（MIT） | 可选底座，视需要引入 |

**最重要的判断**：我们不需要"栅格→矢量"（用户画的是矢量），不需要"通用 BIM 内核"
（我们只要体量级的建筑语义），也不需要第三方投影内核（宿主已有）。
**这是一个纯自研 + 宿主能力 + 现有参数复用的活儿**，这正好是插件最擅长的地方。

### 2.4 调研给出的四条产品级结论（三家产品一致）

| 结论 | 证据 | 对计划的约束 |
|---|---|---|
| **① 没有一家承诺全自动** | ACA 生成后仍需"更新/编辑线条"；天正社区实测立面存在女儿墙/阳台栏杆对不上、标高轴号不显示、门窗立面缺失；"不可能全部都可以生成，还需要人为修改" | 定位为"**高覆盖率 + 可编辑 + 问题清单**"，把人工干预入口当功能做（§7 难点 7） |
| **② 必须有自己的构件对象** | 天正明确"普通 CAD 画的图不行"；BricsCAD BIMIFY 也要求先有 3D 实体 | **构件化绘制**是一条正式输入通道，与"反推老图"并列（§2.1、§10 问题 2） |
| **③ 产出清单固定** | BricsCAD BIMIFY 的 "Create sections: an elevation view and a plan section per floor" | v1 验收固定为"**每层一张平面剖切 + 四面立面**"，防止范围蔓延 |
| **④ 标注与详图不参数化** | Revit/ArchiCAD 视图是"模型的一次求值"，标注独立叠加；广联达官方"注释走二维辅助设计" | 投影结果做成**可重算对象**，标注继续用我们现有标注体系叠加；**不做**"视图线稿反向回写模型" |

**已知深水区（三条）**：① 墙接头（T/L/十字）与厚度归并；② 洞口归属与门窗立面参数缺失；
③ 楼梯/坡道/屋顶的竖向建模。学术侧的系统性综述见
[Yin, Wonka, Razdan, IEEE CG&A 2009](https://doi.org/10.1109/MCG.2009.9)；
工程解法可参考国内专利
[CN113642065A](http://patentimages.storage.googleapis.com/23/c5/ad/092f82e733f885/CN113642065A.pdf)
的"**人工筛图层 + 三角剖分 + 合并规则 + 缝隙线修补**"思路（我们的"问题清单 + 手工补墙段"就是它的产品化）。

## 3. 现有资产盘点：能直接白拿的参数（计划的地基）

| # | 资产 | 位置 | 在模型里直接干什么 | 还需要补什么 |
|---|---|---|---|---|
| 1 | **图层角色表** | `DraftingLayerRoles.cs`（23 图层，含"使用方"） | 识别图纸里哪些线是门窗、楼梯、注释 | **新增"建筑构件"组**：轴网/墙/柱/梁/楼板/屋顶/房间/标高/洞口 |
| 2 | **制图标准** | `DraftingStandardService.cs`（图层色/线型/线宽、文字/标注/引线样式、标注参数、比例） | 生成视图的图层、线型、线宽、文字与标注样式全部从这里取，**不再写死** | 新增剖面/立面专用图层键（背景线、剖切线、剖切填充、门窗编号、标高、轴号） |
| 3 | **标准读取桥** | 楼梯模块的 `DraftingStandardBridge.LayerName(key, fallback)` | 已经验证过"外部模块复用主插件制图标准"的做法 | 照它写一个 `BuildingModelBridge` |
| 4 | **门窗参数（最强复用）** | `DoorWindowElevation.cs`：宽/高/窗台高/类型/分格预设/开启方式/安装缝/外框/中挺/门框/凸窗左右深度与分格/材料/图集/分格自定义 | ① 三维里**打洞口**；② 立面里**画门窗**（分格、开启线、凸窗出挑全都有参数）；③ 门窗表/编号联动 | 补"门窗在墙上的位置（沿墙定位）"：从块参照/天正对象取 |
| 5 | **门窗表读取** | `TianzhengDoorWindowService`（读天正门窗表/原生表格/散文字） | 把"编号 → 宽高/类型/材料"对上立面与三维 | 需要"图纸里的门窗对象 ↔ 表里编号"的匹配规则 |
| 6 | **楼梯参数** | `StairProjectDefinition`（`Storeys[].Height`、跑数、踏步、平台、楼板、梁）+ 已验证的 `DrawingView`/`CadLineRenderer` | ① 模型里的**层高来源**之一；② 三维楼梯体量；③ 剖面直接复用现有生成器 | 需要"楼梯在平面上的位置 + 与楼层的绑定" |
| 7 | **房间（天正对象）** | `TianzhengRoomService`：`TCH_SPACE` 的名称/面积 | 房间名称、面积表、楼板轮廓来源 | 无天正对象时需要"闭合多段线 + 文字"推断 |
| 8 | **抽象视图 + 渲染器** | 楼梯模块 `Geometry\DrawingView.cs`（线/文字/标注/表格/填充/图名/引线/比例）与 `CadLineRenderer.cs` | **这是本功能最好的架构先例**：模型 → 抽象视图 → 按图层写成 CAD 实体 | 把这一层抽成主插件可用（详见 §5.4） |
| 9 | **大样排版引擎** | `DetailLayoutService.ComputeLayout/Insert`（分栏/分页/容量/图框锚点/比例） | 生成的立面/剖面**自动排版**到图框 | 无（直接用） |
| 10 | **图框登记** | `FrameDefinition`（纸张/方向/打印比例/图名图号属性标签/模板 DWG） | 视图标题、图号、比例、插入图框 | 无（直接用） |
| 11 | **图纸目录** | `Catalog` + `SheetCatalogItem` | 生成的立面/剖面进目录 | 无（直接用） |
| 12 | **项目管理 / 云同步** | `ProjectProfile`（含 `CloudId`）、`PublishPlanStore` | 模型文件随项目走、随云同步、可改名不重传 | 模型文件加入项目文件夹约定 |
| 13 | **填充素材** | 用户配置 `填充素材\*.pat`（混凝土等） | 剖面材质填充 | 材质 → PAT 的对照表 |

**没有的（必须新建）**：构件图层组、**楼层表（层名/标高/层高）**、轴网对象、模型文件格式、
识别器（墙/洞口/房间）、三维体量生成器、投影管线、标注器、模型编辑器。
全仓库目前**没有任何三维实体或投影代码**（已 grep 确认），所以这是一次从零开始、但地基很好的建设。

## 4. 产品形态与用户流程

### 4.1 命令（功能简称必须四字，构建脚本会校验）

**A. 构件化绘制（P0.5，新图走这条）**

| 命令（暂定） | 名称 | 干什么 |
|---|---|---|
| `HQ` | 画墙 | 拉轴线成墙，厚度/高度取楼层表与制图标准，交点自动清理（T/L/十字） |
| `FMC` | 放门窗 | 在墙上定位放门窗，参数直接取现有门窗表/门窗立面参数库，自动开洞 |
| `BZL` | 布柱梁 | 矩形或按轴网交点批量布置柱、梁 |

**B. 模型与出图（P1–P4）**

| 命令（暂定） | 名称 | 干什么 |
|---|---|---|
| `JZMX` | 建筑建模 | 反推已有图纸：识别报告 → 人工确认 → 生成三维体量（可选留在图里） |
| `MXBJ` | 模型编辑 | 参数面板：楼层表、墙厚墙高、洞口、材质、屋顶、楼梯绑定；改完一键重算 |
| `LMTZ` | 立面投影 | 选方向（东南西北或自定义）与视图比例 → 生成立面（含标高/轴号/尺寸/门窗编号/填充）→ 落图框 |
| `PMTZ` | 剖面投影 | 用剖切符号或交互指定剖切线 → 生成剖面（含剖切填充、梁板断面、楼梯剖面）→ 落图框 |

（可选后续：`MXJZ` 模型检查、`MXMB` 模型模板、`MXDC` 模型导出。命令名与四字简称在开发前统一敲定一次，
并同步进 `FeatureRegistry`、CUIx 菜单与快捷键设置。）

### 4.2 典型流程

```
输入（两条通道，见 §2.1）
 ① 构件化绘制：用我们的命令画墙 / 放门窗 / 布柱梁   ← 新图，识别率≈100%（P0.5）
 ② 反推已有图纸：识别墙 / 门窗 / 房间 / 轴网        ← 老图，半自动 + 问题清单（P0）
        │
        ▼
   建筑模型（building.json：楼层表 + 构件 + 视图定义，随项目走）
        │  ③ 生成三维体量（可选：当前 DWG 或独立"模型.dwg"）
        ▼
   三维模型 ──④ 模型编辑：参数面板 / 改图纸后差异重算──► 模型更新
        │  ⑤ 立面投影 / 剖面投影（可重算的投影对象，带视图范围）
        ▼
   立面/剖面视图（三类线分层 + 填充 + 标注 + 图名）
        │  ⑥ 手工深化后切成 drawing 态，不再被自动重算覆盖
        ▼
   大样排版 / 图框 / 目录 / 发布 PDF
```

### 4.3 明确不做（v1 边界）

- 不做通用 BIM 建模器（不追求 IFC 完整语义、不做构件库平台）
- 不做结构计算、钢筋、算量、能耗
- 不做效果图/渲染、不做幕墙深化、不做异形曲面屋顶（v1 屋顶只做平屋顶 + 常见坡屋顶参数化）
- 不追求 100% 自动（见 §1 第 3 条）；不承诺"改三维实体自动回写模型"（见 §7 难点 7）
- 不做天正专有格式（.tgl 等）的写入，只**读**天正对象的参数

## 5. 技术架构

### 5.1 投影怎么做（本机实测 + API 查证，两条独立证据一致）

**先排除两条不可行的路**（查证结论，见 [AutoCAD 投影 API 调研](调研-AutoCAD三维到二维投影API.md)）：

- **`FLATSHOT`**：只有命令入口，**.NET 没有等价 API**；输出是**匿名块**而不是可控的散线；
  只能靠 `Document.SendStringToExecute` 触发，而它是**异步的**（命令结束后才执行），
  同步调用要走 COM `SendCommand` 或 P/Invoke——工程上不可接受。**不采用。**
- **`VIEWBASE` / `VIEWSECTION` / `VIEWDETAIL`（模型文档）**：**纯命令族，没有公开的 .NET/ActiveX API**；
  依赖 Inventor Interoperability 组件，且视图与 AutoCAD 版本强绑定（换版本打不开/不可编辑）。**不采用。**

**唯一被公开的编程式 3D→2D 通道是 `Section`（SECTIONPLANE）**，两个波段都在：

| 能力 | R24（AutoCAD 2024 本机 `acdbmgd.dll` 24.3） | R25（AutoCAD.NET 25.0.0 `acdbmgd.dll`） |
|---|---|---|
| `Section` 实体与 `GenerateSectionGeometry` | 有 | 有 |
| `SectionSettings`（逐类样式） | 有 | 有 |
| `SectionType` = `LiveSection=1 / Section2d=2 / Section3d=4` | 有 | 有 |
| `SectionState` = `Plane=1 / Boundary=2 / Volume=4` | 有 | 有 |
| `SectionGeometry` = `IntersectionBoundary / IntersectionFill / BackgroundGeometry / ForegroundGeometry / CurveTangencyLines` | 有 | 有 |
| `SectionGeneration` = `SourceAllObjects / SourceSelectedObjects / DestinationNewBlock / DestinationReplaceBlock / DestinationFile` | 有 | 有 |
| `GenerateSectionGeometry(Entity, out Entity[], out Entity[], out Entity[], out Entity[], out Entity[])` | 有 | 有 |

> 注意：托管侧枚举是 `LiveSection/Section2d/Section3d`，`k2dSection/k3dSection` 是 C++/ActiveX 侧名字；
> **托管侧没有 `k2dElevation`**（未找到确证）。所以"立面"不是另一种枚举，而是
> **`Section.State = SectionState.Boundary` + 剖切面法向水平**（剖面则是法向水平 + 加 jogs）。

`GenerateSectionGeometry` 返回的 **5 个数组**与上面的枚举一一对应，这正是我们要的分层依据：

| 输出数组 | 对应枚举 | 在图纸上是什么 | 落到我们的图层 |
|---|---|---|---|
| `intBoundaryEnts` | `IntersectionBoundary` | 剖切到的构件轮廓 | `SectionCut`（粗实线） |
| `intFillEnts` | `IntersectionFill` | 剖切填充 | `SectionHatch`（材质 PAT） |
| `backgroundEnts` | `BackgroundGeometry` | 剖切面之后可见的背景线 | `ElevationBackground`（中实线） |
| `foregroundEnts` | `ForegroundGeometry` | 剖切面之前可见的前景线 | `ElevationOutline`（粗实线） |
| `curveTangencyEnts` | `CurveTangencyLines` | 曲面切线（一般隐藏） | 默认不画 |

`SectionSettings` 提供**逐几何类别**的样式接口（关键）：

```
SetLayer(SectionType, SectionGeometry, string)      SetLinetype(...)     SetLineWeight(...)
SetColor(...)   SetVisibility(...)   SetHiddenLine(...)
SetHatchPatternName(...)  SetHatchScale(...)  SetHatchAngle(...)  SetHatchVisibility(...)
SetGenerationOptions(SectionType, SectionGeneration)   SetSourceObjects(...)  SetDestinationBlock(...)
```

也就是说：**剖切边界、剖切填充、背景线、前景线可以各自落到我们制图标准的图层上，
并直接指定线型、线宽、是否显示隐藏线、填充图案**——"投影回 CAD"这一步的骨架是现成的。

**但有一条硬约束必须写进设计**：可被剖切的实体**只有 `3dSolid / Surface / Body / Region`**
（**Mesh 网格不行，天正的 AEC 墙也不行**）。这意味着：

- 我们不能指望"直接剖切用户图里的东西"（哪怕是天正的墙）——**必须自己生成三维实体**
  （P1 的 `Solid3d` 体量），这与 §2.1/§2.4 的结论是同一个方向；
- 反过来说，**我们自己的体量必须是实体而不是网格**，这一条要写进 P1 的验收。

**复核方法（可重复）**：在 PowerShell 里
`[System.Reflection.Assembly]::LoadFrom('<acdbmgd.dll 路径>')` →
`GetTypes()` 过滤 `DatabaseServices.Section*` → 对 `SectionType`/`SectionGeometry`/`SectionState`/`SectionGeneration`
用 `[Enum]::GetNames(...)` 取值；`GenerateSectionGeometry` 的签名可用 `GetMethods()` 直接看到
（本计划里的签名与枚举值就是这样得到的，与 API 调研报告互相独立、结论一致）。

```
模型（我们自己的体量）
   │ 生成三维实体（墙板柱等，见 §5.3）
   ▼
Section 对象：State = SectionState.Boundary（立面）
              State = SectionState.Plane + jogs（剖面）
   │ 剖切面放进视野（立面放在建筑之外=“从远处看”）
   ▼
GenerateSectionGeometry(...) → 5 组实体
   ▼
按 SectionGeometry 分类落图层/线型/线宽/填充（SectionSettings）
   │
   ▼
后处理：轴号、标高、尺寸、门窗编号、图名、视图框
   ▼
视图定义（可重建）→ 落图框（复用 DetailLayoutService / FrameDefinition）
```

**风险与对策**：`Section` 原生通道虽然可用，但有两处必须在 P2 开头用 spike 验证：

1. **立面语义**：要用 `State = SectionState.Boundary` + 法向水平 + 把剖切面放到建筑之外
   （ArchiCAD 的"从远处看"就是同一个意思），确认五个数组在立面场景下的内容
   （尤其是"背景/前景"是否正好对应"远处可见线/近处轮廓"、隐藏线是否符合制图习惯）。
2. **布尔运算的稳定性**：门窗开洞的标准做法是"挤出墙 → 挤出洞口 → 布尔差"，
   但布尔在部分机器上有崩溃/失败记录（Autodesk 官方博客与 Plant3D 报错 84015 可查）。
   缓解：洞口做成**独立实体**而不是立刻布尔（投影时同样能表达洞口），或按批处理 + 失败重试，
   并提供 `Solid3d.GetSection(Plane) → Region` 这条备用通道取轮廓。

若 spike 结论是"原生不够用"，回退顺序是：
**自研正交投影**（我们的体量以棱柱/长方体为主，隐藏线消除靠面深度排序 + 轮廓剔除，可控且不加依赖）
→ 仍不够才评估 **C++ ObjectARX**（`AcDbSection`/`AcGi` 全量能力，但要维护 C++ 侧，代价最高）
→ 再不行才考虑 OCCT `HLRBRep`（LGPL 动态链接，需附声明 + 可替换 DLL）。

### 5.3 三维体量怎么生成

已核实的 API（R24/R25 均在）：

| 用途 | API |
|---|---|
| 长方体 / 挤出 / 扫掠 / 由 Region 生成 | `Solid3d.CreateBox`、`CreateExtrudedSolid`、`CreateSweptSolid`、`CreateFrom` |
| Region 拉伸 | `Extrude(Region, height, taper)` |
| 布尔并/交/差 | `BooleanOperation(BooleanOperationType.BoolUnite/BoolIntersect/BoolSubtract, Solid3d)` |
| 取剖切轮廓（备用通道） | `Solid3d.GetSection(Plane) → Region` |
| 填充 | `Hatch` + `AppendLoop(HatchLoopTypes, ObjectIdCollection)` + `SetHatchPattern(HatchPatternType.PreDefined/UserDefined/CustomDefined, name)` |

- 墙：按墙段轴线 + 厚度 + 高度（层高 - 板厚）→ 矩形轮廓 **Extrude** 或 `CreateSweptSolid`；
  门窗洞口 → 洞口矩形拉伸成"刀具"做 **布尔差**（`BoolSubtract`）。
  **布尔是主要风险点**（见 §5.1），P1 必须为它准备"洞口实体化（不布尔）"的退路。
- 楼板：房间/外轮廓 → `Region` → 拉伸板厚。
- 柱/梁：矩形/多段线拉伸（v1 可与墙同样处理）。
- 楼梯：复用楼梯模块参数生成体量；剖面**优先直接调用现有楼梯剖面生成器**，
  而不是重新从三维剖切（省事且外观与现有大样一致）。
- 屋顶：平屋顶（板）+ 参数化坡屋顶（双坡/四坡，按檐口/屋脊标高）。
- **实体类型约束**：必须生成 `Solid3d`（或 Surface/Body/Region）——**不能是 Mesh**，
  否则 `Section` 剖不了（§5.1）；这一条进 P1 验收。
- 性能：按"每层一个块（`BlockTableRecord`）+ 分事务提交"组织；
  `WblockCloneObjects` 有内存不释放的已知讨论，避免对整模反复克隆；
  一栋普通住宅（数千面）应在秒级完成。
- 关联填充（`AssociativeHatch`）会在边界变化时自动更新，但**维护成本高**；
  我们生成的是"一次性视图产物"，优先用**非关联填充** + 视图重建（与 §5.4 的 `state` 机制一致）。

### 5.4 视图定义（可重建）与文件格式

模型与视图都存 JSON（与现有项目文件风格一致，`DataContractJsonSerializer` 或手写序列化）：

```
<项目文件夹>\模型\building.json          ← 楼层表 + 构件 + 视图定义
<项目文件夹>\模型\building.json.bak      ← 原子写 + 上一版（沿用现有做法）
<项目文件夹>\模型\views\<视图名>.json    ← 单个视图的缓存（可选）
```

```jsonc
{
  "version": 1,
  "project": "山水湾四期",
  "cloudId": "山水湾四期-42ab264ee1",            // 与项目同一身份，改名不换（复用现有机制）
  "storeys": [ { "id": "1F", "name": "一层", "elevation": 0, "height": 3600,
                 "sourceDwg": "…\\一层平面.dwg",     // 该层的来源图纸
                 "planRange": [0,0,42000,18000],    // 平面在图纸中的范围
                 "basePoint": [100000, 50000],      // 图纸上的基点
                 "planToBuilding": [1,0,0,1,0,0] }, // 图纸坐标 → 建筑坐标（旋转/镜像/比例）
               { "id": "2F", "name": "二层", "elevation": 3600, "height": 3300,
                 "standardOf": "1F" } ],            // 标准层：复用一层的构件，只换标高
  "grids":   [ { "id": "1", "direction": "vertical", "position": 0 },
               { "id": "A", "direction": "horizontal", "position": 0 } ],
  "walls":   [ { "id": "w1", "storey": "1F", "start": [0,0], "end": [7200,0],
                 "thickness": 200, "height": 3500, "material": "加气混凝土",
                 "openings": [ { "uid": "o-8f3a…", "code": "C1218", "type": "窗",
                                 "offset": 1200, "width": 1200, "height": 1800,
                                 "sill": 900, "source": "TCH_OPENING:1F#23",
                                 "confirmed": true } ] } ],
  "slabs":   [ { "id": "s1", "storey": "2F", "outline": [[0,0],[7200,0],[7200,5400],[0,5400]],
                 "thickness": 120, "elevation": 3500 } ],
  "columns": [], "beams": [],
  "stairs":  [ { "id": "st1", "storey": "1F", "seat": [1200,3000], "rotation": 0,
                 "params": "楼梯项目：主楼梯" } ],   // 只存引用，楼梯算法仍归楼梯模块
  "roofs":   [ { "id": "r1", "type": "平屋顶", "elevation": 10500, "outline": [] } ],
  "spaces":  [ { "id": "sp1", "storey": "1F", "name": "客厅", "area": 32.5, "outline": [] } ],
```

**三个必须写进数据模型的规则**（来自并行评审稿的实践要点，已并入本计划）：

1. **每层都要有"图纸坐标 → 建筑坐标"的变换**。实际项目里多层平面常常**并排画在同一张 DWG**，
   还可能用到 UCS、旋转、镜像、图块插入比例；直接拿原始坐标叠楼层必错。因此每层记录
   `sourceDwg / planRange / basePoint / planToBuilding`，由它换算出建筑坐标。
2. **参数要带来源与确认状态**：`值 + 单位 + 来源 + 是否已确认 + 修改版本`。
   优先级固定为 **已确认的实例覆盖 > 项目统一类型 > 原模块导入值 > 建议默认值**；
   **缺失值绝不能静默当成零或默认值**（例如窗台高未知时，标"缺参数"而不是按 900 画）。
   再次导入图纸产生**差异清单**由用户逐条确认，不覆盖用户已改过的值。
3. **门窗编号不是实例身份**：同编号可以有多樘、不同朝向/楼层/翻转，**每樘一个 GUID**
   （`openings[].uid`）；图纸侧的绑定用 `DrawingGuid + ElementId + EntityHandle`
   （`ObjectId` 不跨会话持久化，`Handle` 也不能单独作全局身份）。

视图定义单独成段（`views`）：

```jsonc
  "views": [ { "id": "v1", "kind": "elevation", "direction": "south", "scale": 100,
               "storeys": ["1F","2F"], "title": "南立面图",
               "cutPlaneOffset": 20000,      // 立面：剖切面放在建筑之外（ArchiCAD 的“从远处看”）
               "viewDepth": 60000,           // 视图深度（对齐 Revit 视图范围）
               "showBeyond": true,           // 是否画“超出”线
               "scope": "all",               // all / selected（对应 Section.SetSourceObjects）
               "state": "model" },           // model=跟随模型可重算；drawing=已手工深化，停止自动重算
             { "id": "v2", "kind": "section", "cutLine": [[3000,-2000],[3000,8000]],
               "viewDepth": 6000, "scale": 50, "title": "1-1 剖面图", "state": "model" } ]
```

> **视图定义必须带"视图范围"**（剖切面位置 / 视图深度 / 是否画超出线 / 参与对象范围），
> 这是 Revit 视图范围与 ArchiCAD 立面"从远处看"的规则化（§2.2）；
> `state` 字段对应 ArchiCAD 的 Model/Drawing 状态与 ACA 的"可更新"：
> **一旦用户开始手工深化这张立面，就切成 `drawing`，不再被自动重算覆盖**——
> 这条规则能避免"模型一改，人工修改全丢"这种最招人恨的行为。

**与现有 ID 的映射（这是"复用现有参数"的落点）**：

| 模型字段 | 来源 | 备注 |
|---|---|---|
| `openings[].code/width/height/sill/分格/开启/材料/图集` | **门窗参数**（`DoorWindowElevationPreference` / 门窗表） | 只存编号，立面绘制时**调用现有门窗立面生成器**，不复制参数 |
| `openings[].uid / hostWallId / offset / floor` | 图纸侧识别或构件化绘制 | **编号只是类型**，实例身份用 GUID；同编号多樘、不同朝向/楼层/翻转都要能区分 |
| `storeys[].height` | 楼梯模块层高、或用户在楼层表里填 | 两者冲突时以楼层表为准并提示；**不允许两套层高数据互相覆盖**（楼梯算法仍归楼梯模块） |
| `stairs[].params` | 楼梯模块 `StairProjectDefinition` | 只存引用，不复制 |
| `storeys[].sourceDwg/planRange/basePoint/planToBuilding` | 平面登记 | 图纸坐标 → 建筑坐标（UCS/旋转/镜像/比例） |
| 图层名 | **制图标准** `DraftingStandardService` | 通过 `BuildingModelBridge` 读取 |
| 文字/标注样式、比例 | 制图标准 + `DrawingScaleService` | 生成标注时使用 |
| `spaces[].name/area` | 天正房间对象 / 闭合多段线 + 文字 | |
| 材质 → 填充图案 | 用户配置 `填充素材\*.pat` | 需要一张材质对照表（可编辑） |
| 图纸绑定 `CadBinding` | `DrawingGuid + ElementId/ViewId + EntityHandle` | `ObjectId` 不跨会话持久化，`Handle` 不能单独作全局身份；DWG 另存/复制/粘贴要有检测与恢复 |

### 5.5 视图产物长什么样

以"南立面"为例，生成的实体按图层分组（图层键新增到制图标准）：

| 图层键（新增） | 内容 | 默认线型/线宽 |
|---|---|---|
| `ElevationOutline` | 建筑外轮廓、可见转折线 | 粗实线 |
| `ElevationBackground` | 背景可见线（远处墙面、台阶、雨篷） | 中实线 |
| `ElevationHidden` | 需要表达的虚线（如雨篷投影、洞口） | `HIDDEN` |
| `ElevationDoorWindow` | 门窗（**复用门窗立面生成器**：分格、开启线、凸窗出挑） | 中实线 + 开启线 |
| `ElevationGround` | 室外地坪线（加粗） | 特粗实线 |
| `SectionCut` | 剖面剖切线（被剖到的墙板断面轮廓） | 粗实线 |
| `SectionHatch` | 剖面剖切填充（材质 PAT） | 填充 |
| `SectionBeam`/`SectionSlab` | 梁板断面 | 粗实线 + 填充 |
| `ElevationGrid`/`SectionGrid` | 轴号与轴线（立面只画轴号与竖向轴线） | 点划线 |
| `ElevationLevel` | 标高符号与标高值 | 细实线 + 文字 |
| `ElevationDimension` | 竖向尺寸（层高、门窗定位） | 标注样式 |
| `ViewTitle` | 图名与比例（复用图名标注做法） | 文字 + 下划线 |

**线的三分类**（照 Revit 视图范围，直接决定线宽是否"像施工图"）：

| 类别 | 含义 | 线宽 | 图层键 |
|---|---|---|---|
| **剖到** | 与剖切面相交的构件（剖面里的墙板梁断面、门窗框） | 最粗 | `SectionCut` + `SectionHatch` |
| **投影** | 剖切面之前/之后可见的构件轮廓（立面里的凹凸、雨篷、台阶） | 中 | `ElevationOutline` / `ElevationDoorWindow` |
| **超出** | 视图深度以外的构件（远景、屋脊之后的轮廓） | 细/虚线 | `ElevationHidden`（`showBeyond` 控制） |

**大样怎么做**：`模型截取 + 构造规则/模板 + 人工补绘`——
模型只提供**真实位置与尺寸**，防水搭接、保温收口、密封胶、预埋件这类参数模型里没有，
**不能凭空生成**；第一批优先做楼梯、门窗、窗台节点，复用现有专业出图规则，输出标明"待补参数"。

**比例与表达分级**（避免"所有细节都做成实体"）：

| 出图比例 | 表达重点 |
|---|---|
| 1:100 / 1:50 | 主体轮廓 + 洞口 + 填充，门窗分格按类型简化 |
| 1:20 | 增加门窗框、饰面层、材料层 |
| 1:10 / 1:5 | 用节点规则 + 人工补绘；门窗详细分格作为**二维语义叠加**，不追求实体化 |

## 6. 分阶段开发计划

> 人日按"一个熟悉本仓库的开发者"估，含自测；不含需求反复。

### P0 图纸解析与模型文件（约 8–12 人日）

**目标**：不生成任何三维，只把"图纸 → 模型参数"这条路走通，并给出可核对的问题清单。

**识别的优先级阶梯**（由可靠到不可靠，**上一级能用就不用下一级**）：

| 级别 | 来源 | 可靠性 | 处理方式 |
|---|---|---|---|
| 1 | **插件自己登记的构件**（P0.5 构件化绘制画的墙/门窗） | 最高 | 直接进模型，零确认 |
| 2 | **天正对象属性适配**（墙厚/墙高/门窗宽高窗台） | 高 | 读属性进模型；版本/对象类型进测试矩阵，读不到就降级 |
| 3 | 动态块 / 属性块（块名或属性含洞口尺寸） | 中 | 需用户确认块名规则 |
| 4 | 标准图层 + 线型（我们制图标准的墙体/洞口图层） | 中 | 按图层角色与几何配对 |
| 5 | 普通双线识别（无图层线索） | 低 | 结果标"待确认"，进问题清单 |
| 6 | 图片 / OCR 辅助（复用 LineVision） | 最低 | 仅作描摹参考，不自动进模型 |

> 前两级是"参数直读"，后四级是"推断"；**界面上必须显示来源与置信度**
> （见 §5.4 的"参数来源与确认状态"规则），用户能一眼看出哪些要核对。

- [ ] 制图标准新增"建筑构件"图层组（墙/柱/梁/楼板/轴网/屋顶/房间/标高/洞口/门窗定位）
- [ ] 新增**楼层表**参数（层名/标高/层高/是否标准层），随项目保存（沿用 `.ini` + 版本迁移做法）
- [ ] 模型文件读写（`building.json`，原子写 + `.bak`，随项目文件夹）
- [ ] **墙识别**：双线配对（含天正墙对象直读）；输出墙段（轴线/厚度/长度）
- [ ] **洞口识别**：天正门窗对象优先；否则"块参照 + 洞口图层 + 宽度配对"
- [ ] **房间识别**：天正 `TCH_SPACE` 优先；否则闭合多段线 + 文字匹配
- [ ] **轴网识别**：轴线图层 + 轴号文字（可选，缺失时允许手工指定）
- [ ] **识别报告窗口**：构件计数 + 问题清单（未闭合墙、孤立门窗、缺层高、重叠墙），
      点一条能缩放到图上对应位置
- [ ] 纯逻辑单元测试（墙段生成、双线配对、洞口归属、坐标换算）

**验收标准**：
1. 在 **3–5 张真实图纸**（含 1 张纯 AutoCAD、1 张天正）上，墙段识别正确率 ≥ 90%（人工核对），
   门窗归属墙段正确率 ≥ 90%；
2. 每张图纸的问题清单条数 ≤ 20 条量级，且每条都能定位；
3. 模型 JSON 可被下一个版本读回，字段无丢失；对同一张图纸重复识别的结果**完全一致**（幂等）。

**风险**：双线墙的"断线/斜墙/墙厚不一致"会让配对失败 → 对策是"识别 + 提示 + 手工补墙段"
（在报告里允许手工指定墙段），不追求全自动。

### P0.5 构件化绘制（约 8–12 人日，强烈建议与 P0 并行或紧随其后）

**为什么必须有这一阶段**：调研里最硬的一条事实是——**天正拒绝解析普通多段线，ACA 要求自己的 AEC 对象，
BricsCAD BIMIFY 也要求先有三维实体**。也就是说"从任意二维线稿全自动推断构件"在商业产品里也不存在。
如果我们只做反推，就永远在跟歧义搏斗；而提供一套自己的参数化构件命令，
可以让**新画的图**走一条识别率接近 100% 的路。

- [ ] **画墙**：指定轴线两端（支持正交/追踪/参照线）→ 厚度与高度默认取"楼层表 + 制图标准"，
      可在面板改；交点自动清理（T/L/十字按中心线裁剪）
- [ ] **放门窗**：在墙上指定位置 → 从**现有门窗参数库**（门窗表/门窗立面参数）选编号或新建 →
      自动开洞 + 生成洞口对象（宽/高/窗台/分格全部来自参数）
- [ ] **布柱/梁**：矩形或按轴网交点批量布置
- [ ] **构件属性面板**：选中构件改参数（复用制图标准的文字样式与现有 WinForms 规范）
- [ ] 构件以 XData/扩展字典记住 `modelId`，与模型文件双向对应（改构件即改模型）
- [ ] 单元测试：墙交角裁剪、洞口定位、参数往返

**验收**：用构件化绘制画一间房（4 道墙 + 2 樘门窗 + 1 根梁），一键成模型，**识别报告零问题**，
立面一次成型（不需要任何手工补墙段）。这条验收一旦通过，"老图反推"就只是兼容功能，而不是主路径。

### P1 三维体量生成与检查（约 10–15 人日）

- [ ] `Solid3d` 体量生成：墙（含洞口布尔差）、楼板、柱、梁、楼梯、平/坡屋顶
- [ ] 生成策略：写入当前 DWG 的"模型图层组"或生成独立 `模型.dwg`（可配置）
- [ ] 按层分块（`BlockTableRecord`）+ 事务分批，保证大图纸不卡
- [ ] **实体类型必须是 `Solid3d`/Region**（Mesh 无法被 `Section` 剖切，见 §5.1）
- [ ] 布尔开洞的**退路**：布尔失败时改为"洞口实体化"并记录，不让整次生成失败
- [ ] **模型检查器**：墙悬空/穿层、洞口超出墙长、板重叠、层高为 0、楼梯与层高不匹配
- [ ] 三维预览：`JZMX` 生成后可选"仅预览体量"（半透明、临时图形），确认后再落图
- [ ] 单元测试：体量生成（面积/体积断言）、洞口扣减正确性

**验收**：一层平面（含 30 樘门窗）生成体量 ≤ 5 秒；模型检查器能报出人为植入的 5 类错误；
生成的体量在 CAD 里可正常剖切显示；**所有构件都是实体**（可被 `Section` 剖切）。

### P2 立面/剖面投影（约 12–18 人日，含 spike）

- [ ] **Spike（1–2 人日，先做）**：用 `Section` + `State=SectionState.Boundary`（法向水平）+
      把剖切面放到建筑之外，调 `GenerateSectionGeometry` 取 5 组几何，逐一核对
      `intBoundary/intFill/background/foreground/curveTangency` 的实际内容与隐藏线表现；
      **结论决定**走"原生投影"还是"自研正交投影"（§5.1 已给出回退顺序）
- [ ] 投影管线：视图定义 → 三维体量 → 投影 → 分类几何 → 抽象视图（`DrawingView`）
- [ ] 渲染器：按 §5.5 的图层表写实体（线型/线宽/填充/门窗调用现有生成器）
- [ ] 标注：标高（层高与洞口）、轴号、竖向尺寸、门窗编号、图名与比例
- [ ] 剖面：剖切符号交互（画剖切线 + 方向）→ 剖面视图；剖切填充用材质 PAT
- [ ] 视图重算：同一视图定义可重复生成（先清旧产物再生成，差量清理）
- [ ] 对拍测试：黄金图纸 → 生成视图 → 断言"图层线数/填充面积/关键尺寸"（防回归）

**验收**：同一张图纸生成南/北立面，轴号、标高、门窗位置与人工绘制的对照图**竖向关系一致**；
剖面能正确表达梁板断面与楼梯；重复生成不产生重复实体；单视图生成 ≤ 10 秒。

### P3 模型编辑器与双向同步（约 12–18 人日）

- [ ] 参数面板（WinForms，按 `docs\CAD_WINFORMS_UI_STANDARD.md`）：楼层表、墙（厚/高/材质）、
      洞口（宽高/窗台/编号）、房间、屋顶、楼梯绑定
- [ ] 改参数 → 差量重算（只重建受影响的体量与视图）
- [ ] **从图纸重读**（re-sync）：图纸改了（墙移动、加窗）→ 重新识别 → **差异对比**
      （新增/删除/修改构件），用户逐条选择接受
- [ ] 构件与图元的绑定：生成的体量打 XData（`modelId`），支持"选中体量 → 编辑器定位构件"
- [ ] 冲突规则写清楚：**模型是唯一数据源**；图纸是输入；改动一律"先更新模型，再重建视图"，
      不提供"直接改立面线稿回写模型"（v1 明确不做，见 §7 难点 7）

**验收**：改一层层高 → 立面上标高与楼层线全部更新，视图定义不变；
从图纸重读后能正确报出"新增 2 樘窗、删除 1 道墙"。

### P4 落图与出图联动（约 6–10 人日）

- [ ] 视图自动排版（复用 `DetailLayoutService`）+ 图框（复用 `FrameDefinition`）
- [ ] 图纸目录（复用 `Catalog`）、PDF 发布（复用 `PdfPublisherService`）
- [ ] 模型文件随项目/云同步（复用 `ProjectProfile` / `CloudId`）
- [ ] 文档：用户手册章节 + README + 构建说明

**验收**：一键把 4 个立面 + 2 个剖面排进 2 张 A2 图框，目录自动出现，能直接发布 PDF。

### P5 可选扩展（按需）

- 图片/扫描图纸 → 模型（复用 LineVision）
- IFC / glTF 导出（xBim CDDL 或 GeometryGymIFC MIT）
- 任意方向/斜向剖切、曲面屋顶、幕墙分格
- 与云同步的"模型版本历史"

## 7. 关键技术难点与对策

| # | 难点 | 具体问题 | 对策 |
|---|---|---|---|
| 1 | 双线墙识别 | 断线、斜墙、墙厚不同、左右墙线分属不同图层、有填充无填充 | 先按"平行 + 端点距离阈值 + 填充/图层加权"配对；失败的墙段进问题清单，允许手工补 |
| 2 | 墙体交接清理 | T/L/十字接头的体积重叠、内墙面接缝 | 体量阶段**允许重叠**（布尔并集求体积），立面投影按轮廓合并处理；不做精细接头建模 |
| 3 | 洞口归属与开洞 | 门窗可能不在墙轴线上、跨两段墙、是非标准块；布尔差在部分机器上有崩溃记录 | 以"洞口中心落在墙段中线容差带内 + 宽度 ≤ 墙段长"归属；跨段时拆分；失败进清单；**布尔失败时退化为"洞口实体化"**（不立刻做差集） |
| 4 | 层高/标高来源 | 图纸上通常没有可靠的层高信息 | **以楼层表为准**（用户填一次），可从楼梯参数/图名/标高符号给建议值；标准层复用 |
| 5 | 立面投影的可见性与隐藏线 | 托管侧**没有** `k2dElevation`；"立面"要由 `State=SectionState.Boundary` + 法向水平实现，且剖切面必须放在建筑之外 | P2 开头 spike 验证（§5.1）；不符则回退自研正交投影，再不行才考虑 ObjectARX/OCCT |
| 5b | 可剖切实体类型受限 | 只有 `3dSolid/Surface/Body/Region` 能被剖切（Mesh、天正 AEC 墙不行） | 自建体量一律生成 `Solid3d`，进 P1 验收；不指望"直接剖切用户图里的东西" |
| 6 | 自动标注 | 标高/轴号/尺寸要"像人画的" | 复用制图标准的标注样式与 `DrawingScaleService` 的比例换算；标注规则做成可配置（哪些标高必标、尺寸链如何合并） |
| 7 | 双向编辑冲突 | 用户既改模型又改图纸；手工深化被自动重算覆盖；删除门窗后编号残留 | 明确"模型为准、视图是产物、图纸是输入"；实行下面 **7 条更新保护规则**；不提供视图反向回写 |
| 8 | 天正对象 vs 纯 CAD | 两类图纸的信息量差一个量级 | 双通道读取（§2.1）；纯 CAD 图纸问题清单更长，界面要明确告知"因为图纸没有参数，所以需要你确认更多" |
| 9 | 性能 | 大图纸 + 大量实体 | 分块/分层/分事务；投影只处理"视图范围内"的构件；`Section` 的 `SetSourceObjects` 限定参与对象 |
| 10 | 与现有功能的边界 | 门窗立面、楼梯大样已经能单独出图 | 明确"模型投影的立面"与"门窗立面大样"是两种图：前者是建筑立面，后者是门窗详图；两者共用门窗参数但互不覆盖 |
| 11 | **竖向构件"对不上号"** | 天正实测：女儿墙、阳台栏杆、雨篷在立面上出不来或位置不对（[社区实测](https://bbs.co188.com/thread-2304684-1-1.html)） | v1 明确列出**支持的构件清单**（墙/门窗/楼板/柱/梁/楼梯/屋顶/女儿墙），清单外的构件一律进"未建模构件"报告，**绝不静默漏掉**；阳台栏杆先按"参数化栏杆"做（可选） |
| 12 | **标高/轴号不显示** | 天正实测立面缺标高轴号（[出处](https://www.zjtcn.com/zhishi/tianzhenglimian)） | 视图定义里**显式声明**要标注的标高（楼层标高 + 门窗定位）与轴号来源；生成后在报告里列出"未标注项"，而不是静默跳过 |
| 13 | **人工深化被自动重算覆盖** | 用户手工改了立面，模型一改就全丢 | 视图带 `state`（`model`/`drawing`）：一旦手工深化即切成 `drawing`，自动重算跳过它并提示（对齐 ArchiCAD 的 Model/Drawing 状态、ACA 的"可更新"） |

**7 条更新保护规则**（并入并行评审稿的要点，P3 的验收依据）：

1. **所有权分离**：自动生成的实体与人工补绘分开放；重算只替换该 `ViewId` 的自动部分，人工内容不动。
2. **更新前给差异**：列出新增/修改/删除与受影响图纸，并允许**一次撤销**。
3. **手工文字与尺寸尽量保留**；锚定的构件消失时标"**失联**"，**不保留看起来正确的旧尺寸**。
4. **删除门窗要同步删掉它自动生成的编号**；用户自己写的说明保留并提示核对。
5. 图纸与模型同时改过 → 产生**候选差异**，由用户选择或逐项合并，**不用"谁新谁赢"**。
6. 首版跨 DWG 以显式"**更新关联视图**"为主，不在用户编辑时偷偷改别的图纸。
7. 多机同时改模型 → 按模型版本**先保存两个版本**，不做静默覆盖（与云同步的冲突策略一致）。

## 8. 测试与验证策略

1. **纯逻辑测试（net8，随现有测试工程跑）**：模型序列化往返、墙段配对、洞口归属、
   投影数学（坐标/方向/比例）、标注排布、视图差量清理。
2. **黄金图纸对拍**：选 3 张代表性图纸（纯 CAD、天正、复杂户型）固化到 `BatchPdfPublisher.Tests\Samples\`，
   生成结果断言语义指标（图层→线数、填充面积、关键标高文字、门窗数量），而不是逐字节比对。
3. **回归保护**：把"识别报告"的计数也做成断言（构件数、问题数），防止识别规则悄悄退化。
4. **实机验收**：每个阶段都产出一份 `docs\history\` 记录，写清"实际核实过的事实"与"未证实项"
   （沿用本仓库既有文档纪律）。

## 9. 风险登记

| 风险 | 影响 | 概率 | 缓解 |
|---|---|---|---|
| 立面投影的原生能力不符合制图要求 | P2 需要自研投影，工期 +5～8 人日 | 中 | P2 开头先做 spike，结论出来再决定 |
| 墙体识别在真实图纸上达不到 90% | 用户觉得"不如自己画" | 中高 | 半自动定位 + 问题清单 + 手工补墙段；先在 3 张图纸上验证再往下走 |
| 图纸没有层高/轴网信息 | 立面缺标高与轴号 | 高 | 楼层表必填（引导填写），轴网可选 |
| 天正版本差异（T20/T30、不同专业） | 对象读取不稳 | 中 | 只读少数属性（厚度/高度/宽高/窗台），失败即回退图形反推并提示 |
| 三维实体留在 DWG 里导致文件变大 | 用户抱怨 | 中 | 默认生成独立"模型.dwg"或按层分块；提供"清理模型体量"命令 |
| 功能过多导致菜单/面板膨胀 | 使用门槛 | 中 | 归入"建筑模型"面板（4 个按钮），与现有 18 个功能并列而非插入 |

## 10. 需要你拍板的 9 个问题

1. **构件化绘制要不要做**（P0.5，约 8–12 人日）：调研里最硬的一条事实是——天正明确"普通 CAD 画的图不行"，
   ACA、BricsCAD 也都要求自己的构件对象。**"从任意二维线稿全自动推断构件"在商业产品里并不存在。**
   所以我建议除了"反推老图"，再加一条"**用我们自己的命令画墙/放门窗**"的主路径：新图识别率接近 100%。
   你更倾向于哪条为主？（如果只做反推，我能承诺的准确率上限要低不少）
2. **v1 的定位**：是"生成模型 + 立面剖面出图"就够，还是必须包含房间面积表 / 门窗表联动？
3. **输入图纸**：你实际画的图主要用**天正对象**还是**纯 AutoCAD 线**？（决定识别器工作量与准确率上限）
4. **层高与标高**：接受"必须填一次楼层表"吗？（不接受的话，自动推断的准确率我无法承诺）
5. **半自动**：接受"识别 + 问题清单 + 人工确认"这种节奏吗？（天正做不到，我们也不该承诺）
6. **三维模型放哪**：默认放进当前 DWG（直观、文件变大），还是生成独立 `模型.dwg`（干净）？
7. **剖面/立面范围**：v1 只做正南北东西四个方向 + 直线剖面，够不够？
8. **是否要 IFC 交付**（给结构/机电/审查用）？如果要，我会选 xBim（CDDL，明确允许闭源商用）或
   GeometryGymIFC（MIT），这会增加约 5–8 人日与一个新的 DLL 依赖（安装清单要同步改）。
9. **优先级**：这个功能与"把现有发布/门窗/楼梯再打磨"相比，你希望先做哪个？如果并行，
   我可以先把 **P0 + P0.5**（构件化绘制 + 识别 + 报告，**不动三维**）做成可试用的最小版本 ——
   这部分单独就有用：即使不做模型，参数化画墙与门窗本身就能提升绘图效率。

## 11. 里程碑与投入建议

| 里程碑 | 内容 | 人日（估） | 可见成果 |
|---|---|---|---|
| M0 | P0.5 构件化绘制（画墙/放门窗/布柱 + 属性面板） | 8–12 | **新图可以直接用参数化构件画**，识别率≈100%（单独就有价值） |
| M1 | P0 识别 + 报告 + 模型文件 | 8–12 | 能在自己图上看到"识别出的墙/门窗/房间 + 问题清单" |
| M2 | P1 三维体量 + 检查 | 10–15 | 一键生成体量，可在 CAD 里转着看 |
| M3 | P2 立面/剖面投影 | 12–18 | **立面和剖面能出图**（本功能的里程碑） |
| M4 | P3 编辑器 + 差异同步 | 12–18 | 改参数/改图纸都能重算 |
| M5 | P4 落图出图联动 | 6–10 | 一键排版 + 目录 + PDF |
| 合计 | M0–M5 | **56–85 人日** | 一条完整的"平面 → 模型 → 立面剖面 → 交付"链路 |

**建议的推进方式**：先做 **M0（构件化绘制）+ M1（识别与报告）**，约 3–4 周，拿**你自己的真实图纸**验证。
这两步**不依赖任何三维能力**，却已经能解决"画的时候就带着参数"和"老图能被读成构件"两件事；
验收标准清楚（M0 零问题清单、M1 识别率 ≥ 90%），是**整个计划里风险最低、信息量最大**的一步。
M0/M1 通过后再决定是否投入 M2–M5。

**最先动手的样板**（不要一上来做界面或集成整套 BIM）：
**"现有楼梯参数 + 一面带窗的墙 + 一块楼板"** —— 把这三样从参数走到三维、再走到一张立面/剖面，
整条链路就验证完了。之后再扩到多层、多构件。

**完整的验收脚本、性能预算数字与几何误差目标**见并行评审稿
[建筑模型与 CAD 联动：案例调研与开发计划](plans/建筑模型与CAD联动-调研及开发计划.md)
第 10–13 节（它给出的门槛可直接用作我们的 P1–P4 验收）：包括三层并排平面的样例、
"改一樘窗宽 → 只更新受影响视图"的 10 步核心操作、以及
"普通建筑尺寸几何误差 ≤ 0.1 mm、1000 构件三层预览 ≤ 2 秒、单立面出图 ≤ 5 秒"这类可测目标。

## 附：术语

| 术语 | 含义 |
|---|---|
| 体量模型 | 只有几何与少量属性（层高、墙厚、材质）的建筑模型，不做完整 BIM 语义 |
| 视图定义 | 描述"从哪看/在哪剖/比例多少/包含哪些楼层"的可重建对象 |
| 抽象视图 | `DrawingView` 这类与 CAD 无关的二维产物（线/文字/标注/填充），由渲染器写成 CAD 实体 |
| 投影管线 | 模型 → 三维体量 → 剖切/投影 → 分类几何 → 抽象视图 |
| 问题清单 | 识别阶段无法确定、需要人工确认的条目（未闭合墙、孤立门窗、缺层高等） |

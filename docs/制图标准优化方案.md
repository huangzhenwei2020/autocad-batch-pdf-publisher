# 制图标准（BZS）优化方案

> 本文只做设计与改动清单，不含代码改动。
>
> **两条硬约束（用户原则）**：
> 1. 每个图层都要真正有作用；
> 2. 场景中同名图层的参数要被覆盖。
>
> 核查结论：**这两条现在都没做到**——
> 17 个图层里 9 个从来没有任何代码使用（纯装饰行）；
> 覆盖场景的开关被 `CreateOnApply` 挡掉（`DraftingStandardService.cs:176`），
> 取消"创建"勾选的行即使勾了"同步更新已有图层"也不会覆盖；
> 图像转 CAD 与楼梯大样还各自写死图层名，完全绕过标准；
> 另有 1 处会静默丢失用户标准的容错缺陷。
>
> 设计上按你给的截图形态收敛为**一张图层表**：图层名可改，
> 但由只读的**系统标签**做插件取层锚点，表内每行都有"使用方"与"快捷键"。
> 修好这些再谈界面，标准才立得住。

## 1. 现状核查：标准到底有没有被使用

### 1.1 全链路

```
DraftingStandardProfile（17 图层 + 3 文字样式 + 1 标注样式 + 1 引线样式）
        │
        ├─ 存储  drafting-standard.ini        （LayerItem.N.* / Text.N.* / Dimension.* / Leader.*）
        │
        └─ 应用
             ├─ EnsureAll / ApplyConfiguredResources      创建资源
             ├─ EnsureFrameLayer                          图框
             └─ DrawingScaleService.ApplyStandardizedScale 比例更新时改文字与标注
```

### 1.2 逐个资源的真实使用情况

对 `DraftingStandardService` 中每个图层/文字样式常量做全仓库引用统计，
排除 `DraftingStandardService.cs` 与 `DraftingStandardForm.cs` 自身：

| 常量 | 外部引用 | 结论 |
|---|---|---|
| `FrameLayer`（WL-图框） | 有 | 图框、大样排版在用 |
| `CatalogLayer`（WL-目录） | 有 | 目录插入在用 |
| `AnnotationTextLayer`（WL-注释-文字） | 有 | 图框属性、门窗立面在用 |
| `AnnotationDimensionLayer`（WL-注释-标注） | 有 | 归层在用 |
| `BodyTextStyle` / `TitleTextStyle` / `AnnotationTextStyle` | 有 | 图框、目录、门窗、比例在用 |
| `ArchitectureOutlineLayer`（WL-建筑-轮廓） | **0** | **死标准** |
| `ArchitectureFineLayer`（WL-建筑-细线） | **0** | **死标准** |
| `ArchitectureStructureLayer`（WL-建筑-结构） | **0** | **死标准** |
| `ArchitectureHiddenLayer`（WL-建筑-隐藏） | **0** | **死标准** |
| `ArchitectureHatchLayer`（WL-建筑-填充） | **0** | **死标准** |

这 5 个"建筑类"常量的唯一出现位置是
`DraftingStandardService.cs:353` 的 `CreateDefault()` 那一行——即只把名字填进了列表。

**后果**：用户在"一键创建勾选项"里勾上建筑轮廓/结构/填充，图纸里会多出这些空图层，
但插件画的任何图元都不会进这些层。图层页因此有一半是装饰性的。

### 1.3 绕过标准的模块（✅ = 已修复，见 §9.7）

| 模块 | 原状 | 现状 |
|---|---|---|
| 图像转 CAD<br>`LineVisionCadWriter.cs` | 硬编码 `LV-LINE-H`/`LV-TEXT` 等 7 个层，颜色各自写死；文字用 `Database.Textstyle` | ✅ 改为 `DraftingStandardService.EnsureLayerFor` 按标准取层；文字改用标准的"标注"样式。已无任何写死的 `LV-*` |
| 门窗立面<br>`DoorWindowElevationInsertionService.cs:672-674` | 硬编码 `WL-门窗-窗/门/开启洞口`，而这 3 个层**标准里根本没有** | ✅ 已加入标准（3 个新键）并改为按标准取层 |
| 大样排版<br>`DetailLayoutService.cs:551,553,561,563` | 硬编码 `WL-大样-分隔`/`WL-大样-索引`，标准里同样没有 | ✅ 已加入标准（2 个新键）并改为按标准取层 |
| 楼梯大样<br>`StairDetail/.../CadLineRenderer.cs:17-27` | 硬编码 7 个图层名；仅反射借用了标注样式 | ✅ 已改为经 `DraftingStandardBridge` 读标准，失败回退内置常量（见 §9.8） |

**发现并修复的一个隐患**：`EnsureRequiredStairLayers` 只按 `"Stair"` 前缀补齐图层，
所以**老用户的 `drafting-standard.ini` 永远拿不到新版新增的键**。
已改为通用的 `RefreshRequiredLayers(profile, prefix)`，并对
`DoorWindow`/`Detail` 一并补齐，否则旧配置上这些功能会悄悄退化回硬编码。

楼梯这条尤其可惜：标准里已经为它定义了 8 个图层，但用户在标准面板里改颜色、改名字，
楼梯大样输出一点反应都没有——因为模块用的是自己的常量。

### 1.4 另外三处

1. **`DimensionScales` 是死字段**：`DraftingStandardService.cs:72` 与
   `DraftingStandardForm.cs:165` 都强制写 `{1}`，没有任何读取方。
   （真实的多比例标注样式由 `EnsureDimensionStyleForScale` 按需创建，与这个字段无关。）
2. **线型候选不全**：图层页线型下拉只有 `Continuous/HIDDEN/CENTER/DASHED`
   （`DraftingStandardForm.cs:90`），而标准默认值里就用了 `DASHDOT2`
   （`DraftingStandardService.cs` 楼梯轴线）。当前值不在候选列表里，
   用户一旦动过这一格就再也选不回来。
3. **`BZSAPPLY` 与 `BZSINITARROWLIB` 是"孤儿命令"**：
   `RibbonService.cs:67-79` 与 `MenuService.cs:61-64` 都**只**遍历
   `FeatureRegistry.All` 生成入口，而登记表里只有 `BZS`（`FeatureRegistry.cs:23`）。
   这两个命令因此没有 Ribbon 按钮、没有经典菜单项、也无法在快捷键设置里出现——
   只能靠手输命令名调用。注意"一键应用"本身并没有缺失
   （BZS 面板里的"保存并一键创建勾选项"按钮会走 `ApplyConfiguredResources`），
   缺的是**独立命令的可见入口**；若要给它入口，登记表新增一条即可。

### 1.5 会静默丢标准的容错缺陷（P1 的核心）

```csharp
// DraftingStandardService.cs:85
catch { return DraftingStandardProfile.CreateDefault(); }
```

`LoadProfile()` 吞掉**所有**异常直接回默认。INI 任意一行格式异常、文件被占用、
磁盘瞬时错误，用户的整套标准都会**无声无息变回默认值**，面板还会把默认值显示出来，
用户无法察觉自己的设置已经没了。

对比：`PublishPlanStore.LastRecoveryNotice` 与 `CloudSyncSettingsStore.LastRecoveryNotice`
都有恢复提示机制并会展示给用户（`PublisherViewModel.cs:94`、`CloudSyncSettingsForm.cs:200`）。
制图标准是这套机制里**唯一漏掉的一个**，偏偏它丢的是用户手工填的 40 个参数。

## 2. 设计总原则

1. **一份标准，全部生效**。凡是插件往图里写图元/文字/标注的地方，
   都必须从标准取图层与样式；取不到才回退内置默认，并且**回退要在界面上可见**。
2. **表是唯一真相**（本次新增的核心约束）。
   一张图层表同时承载图层名、参数、快捷命令、说明与"谁在用"；
   插件只按**稳定的系统标签**取层，用户可随意改图层名。
   每个图层都必须有真实消费方，同名图层的参数要被表覆盖。
3. **标准必须可移植、可恢复**。能导出/导入，损坏时保留可用部分并明确告知。
4. **模型内外一致**。面板上看到的即图元实际用的，不存在"改了没反应"的格子。

## 3. 核心设计：图层表 + 覆盖到场景

### 3.0 两条硬约束（用户原则）

> 1. **每个图层都要真正有作用**——表里不允许存在装饰行。
> 2. **场景中同名图层的参数要被覆盖**——表是唯一真相，应用时改过来。

上一版方案用"前缀体系 + 角色枚举"表达这两点，绕了。按截图那张表的形态，
直接把**一张图层表**作为唯一模型更直白，也让"每个图层有自己的命令/快捷键"
自然成立（表里本就有"快捷键"列）。

### 3.1 参考形态（来自 `幕速工具箱` 截图）

界面形态照这张表：

```
[新建图层][图层选择][拾取图层][智能匹配][批量绑定][清空列表]
[重置图层][加载快捷键][导入配置][解析图层][导出配置][导出图例]

☑ 拾取 │ 图层名称 │ 系统标签 │ 颜色 │ 线型 │ 线型比例 │ 打印 │ 快捷键 │ 说明
☑  ⊕  │100-建筑文字│100-建筑文字│ 50 │Continuous│      │  ☑  │        │建筑图纸文字注释
☑  ⊕  │101-轴线   │101-轴线   │250 │ DOTE    │      │  ☑  │        │结构轴线与网格绘制
...
```

| 列 | 作用 | 本轮处理 |
|---|---|---|
| 拾取 | 从场景里拾一个对象，取其图层回填该行 | 采纳 |
| **图层名称** | 真正写进图纸的图层名，**用户可改** | 采纳 |
| **系统标签** | 截图里与"图层名称"取值相同，属于冗余列 | **改为稳定的系统标识**（见 3.2） |
| 颜色 / 线型 / 线型比例 / 打印 | 图层参数 | 采纳；线型比例当前标准缺失，需补 |
| **快捷键** | 该图层自己的命令键 | 采纳，且即"每图层有自己的命令" |
| **说明** | 用途描述 | 采纳 |

**两点我必须挑明**：

1. **"系统标签"必须与"图层名称"解耦**。截图里两列取值一样，那就没有信息量。
   但插件运行时需要一个**不随用户改名而漂移**的锚点：
   若只有图层名，用户在表里把 `101-轴线` 改成 `AXIS`，插件就再也找不到它，
   会悄悄回退默认值——这正是本方案 §1 那类"改了没反应"缺陷的根源。
   因此：**系统标签 = 稳定键（只读），图层名称 = 落盘名（可改）**。
   序号逻辑由系统标签承载，实际图层名完全由用户定。
2. 工具栏里"智能匹配/批量绑定/解析图层"的具体语义我**无法从静态截图判定**，
   需要你确认（见 §3.5）。其余按钮语义明确，按字面设计。

### 3.2 模型（一表到底，无前缀体系）

```csharp
public sealed class DraftingLayerRow
{
    // —— 身份 ——
    public string SystemTag;      // 稳定键，只读，由插件定义，如 "ArchText"
    public string LayerName;      // 落盘图层名，用户可改，如 "100-建筑文字"

    // —— 图层参数（表即真相）——
    public short ColorIndex; public int TrueColorRgb = -1;
    public string LineType;  public double LineTypeScale;   // 截图有"线型比例"列
    public int LineWeight;   public bool IsPlottable = true;

    // —— 快捷命令 ——
    public string DefaultShortcut;   // 该图层自己的命令键
    public bool CommandEnabled = true;

    // —— 说明 ——
    public string Purpose;

    // —— 覆盖策略 ——
    public bool SyncExisting = true; // 是否把参数覆盖到场景同名图层
}
```

`SystemTag` 取代上一版的 `DraftingLayerRole` 枚举与前缀体系：
它既是插件取层的锚点，也是表内分组的依据。上一版 §3.2-3.4 的前缀模型**作废**。

### 3.3 约束一：每个图层都要真正有作用

光有"使用方"列还不够——用户看不懂代码，需要**机器可核验**。两件事一起做：

**（1）表内新增"使用方"列**，如实列出消费该图层的模块：

```
图层名称      系统标签      使用方
100-建筑文字  ArchText     图框属性、门窗立面、归层(GL)、图像转CAD
101-轴线      Axis         图像转CAD(轴网)、比例更新
...
（空）        ArchOutline  —— 无
```

**（2）发布期覆盖率自检**：仿 `Test-PlotterMedia.ps1` 那种自检脚本，
新增 `build/Test-LayerUsage.ps1`：

- 扫描 `BatchPdfPublisher` 与 `StairDetail` 源码，收集
  `LayerName("<SystemTag>")` 的实际调用点；
- 与表内每行的 `SystemTag` 对账；
- **有行无引用 → 报"装饰图层"，退出码 1**；
- **有引用无行 → 报"取层回退"，退出码 2**。

这样"每个图层都必须真正被用"从**人的自觉**变成**构建期阻断**。
这是本项目已有先例可循的做法（纸张库就是这么自检的）。

另外，上一版查出的 5 个建筑类死图层，要么接上真实消费方，
要么从表里删除——**不允许以"预留"名义留在表内**。

### 3.4 约束二：覆盖到场景（当前是漏的）

现状缺陷（本轮核对）：

```csharp
// DraftingStandardService.cs:174-181
foreach (var x in profile.Layers.Where(x => x.CreateOnApply))   // ← 只看"创建"勾选
    EnsureLayer(db, tr, x.Name, ..., updateExisting);            // ← updateExisting 才是覆盖开关
```

两层过滤叠加，导致：**取消勾选"创建"的行，即使勾了"同步更新图中已有的同名图层"，也不会覆盖场景**。
用户看到的正是"我明明设了参数，场景里没变"。

改为按 `SyncExisting` 独立判断，与"是否创建"解耦：

```csharp
foreach (var row in profile.Layers)
{
    var exists = layerTable.Has(row.LayerName);
    if (!exists && !row.CreateOnApply) continue;      // 不创建也不覆盖 → 跳过
    if (exists && !row.SyncExisting) continue;        // 存在但不许覆盖 → 跳过
    EnsureLayer(db, tr, row.LayerName, row.Color, row.LineWeight,
                row.LineType, row.IsPlottable,
                update: exists);                      // 存在即覆盖参数
}
```

**覆盖范围必须向用户交代清楚**（避免"怎么把用户数据改了"的投诉）：
覆盖的是**图层表记录**（颜色、线型、线型比例、线宽、打印开关）。
**明确不动的**：图层开关状态、锁定/冻结、图层上已有对象的颜色（对象自身的 ByLayer 会随之显示为新色），
以及任何图元的几何。执行前给出"将覆盖场景中 N 个同名图层"的确认。

**回收站保护**：覆盖前把受影响的图层参数快照到
`图层覆盖-<时间戳>.json`（复用 `PublishPlanStore` 的原子写与备份思路），
提供一键回滚。这是破坏性操作，必须有退路。

### 3.5 待你确认的三点

1. **智能匹配**是什么语义？
   我猜是"把场景里已有的图层按名字/颜色与表行自动配对，建立 图层名↔系统标签 绑定"，
   但截图判不出来。
2. **批量绑定**：是不是"选中多行，一次性绑定到场景中选中的多个图层"？
3. **解析图层**：是不是"扫描当前图纸全部图层，与表对账，列出多余/缺失"？

这三点决定工具栏工作量，先确认再实现，避免我做错方向。

### 3.6 取层接口（不变的核心）

无论模型怎么简化，**消费者必须只有一个取层入口**，替换所有硬编码：

```csharp
public static class DraftingStandardService
{
    public static string LayerName(string systemTag);                       // 按稳定键取图层名
    public static string LayerName(string systemTag, DraftingStandardProfile profile);
    public static ObjectId[] EnsureLayers(Database db, Transaction tr,
        DraftingStandardProfile profile, params string[] systemTags);
    public static ObjectId TextStyleFor(string styleKey);
}
```

**回退必须可见**：任何一次"表里找不到该标签"都记进 `LastFallbackNotice`，
命令结束时用 `Editor.WriteMessage` 回显，而不是静静用默认值。
§4 的消费方改造清单（图像转 CAD、楼梯）在此基础上不变。

### 4.2 楼梯模块的取层方式

楼梯是**独立程序集 + 独立部署**（`WL.Stair.Cad2022/2024/2026`），
不能直接引用主插件类型。两个可选做法：

- **A（推荐）**：在 `WL.Stair.CadShared` 增加 `DraftingStandardBridge`，
  通过 `AppDomain` 反射查找 `BatchPdfPublisher.Services.DraftingStandardService`
  并调用 `LayerName(role)`（与现有 `TryEnsureSharedDimensionStyle` 同一套路数，
  `CadLineRenderer.cs:766` 已验证可行）。取不到就回退内置常量——**行为与今天一致，不会更差**。
- **B**：在主插件侧把"标准快照"写入一个共享 INI，楼梯模块自己读。
  跨进程更松耦合，但多一份解析与两个写入点，容易出现不同步。

选 A。理由：已有可用先例、无新增文件格式、失败时天然回退。

### 4.3 顺手要修的三个小问题

1. **`DimensionScales`**：二选一，不要留死字段。
   - 方案甲：从 `DraftingStandardProfile` 删除，并清理 INI 读写。
   - 方案乙（更好）：真正生效——面板上列出"需要预建的标注样式比例"
     （默认 `{1}`），保存时按列表预建 `WL-标注-1_<scale>`，
     省掉首次出图时按需创建的抖动。**建议乙**，因为它对应用户真实诉求
     （"我希望 1:50 和 1:100 的标注样式一开始就都在"）。
2. **线型候选**：下拉改为"当前图形线型表 + `acadiso.lin` 可加载线型"，
   而不是写死 4 个。至少要把 `DASHDOT2` 等标准默认值补进去，

## 7. 归层功能（切换图层）与统一控制

### 7.1 需求

1. 把**所选对象**归到指定图层。
2. 用户可**自己定快捷**。
3. **统一界面控制**，同时**兼容每个图层拥有自己的命令**。

第 3 条是设计核心：不是二选一，而是**同一份存储、两个入口**。

### 7.2 归层的技术要点（难点不在改 LayerId）

| 点 | 说明 |
|---|---|
| **颜色/线型/线宽随层** | 只改 `LayerId`，若对象属性是**显式**指定的，会原样保留，用户看到"挪过去了但颜色没变"。必须提供"同时设为随层"开关。 |
| **块内对象** | 块参照的 `AttributeReference` 需一并处理；块**定义**内图元不随参照移动。标注的箭头/文字也是块，要明确边界，否则会有部分对象留在原层。 |
| **锁定图层** | 锁定层上的对象跳过并计数，不静默失败。 |
| **视口/布局** | 布局空间与视口内对象的处理范围要明确。 |
| **不可移动对象** | 代理对象、只读对象跳过并计数。 |

执行流程：

```
1. 取选择集：有预选则用预选；无预选则提示 SelectImplied / GetSelection
2. 在事务内逐对象：
   - 目标图层 == 当前图层 → skipped
   - 对象/图层锁定 → locked++，跳过
   - 设 LayerId；若开"随层"，则 Color/Linetype/LineWeight 置 ByLayer
   - 块参照：连带 AttributeReference
3. Editor.WriteMessage 汇总：已归层 N，已在目标层 M，锁定/跳过 K，失败 F
```

全部包在 `document.LockDocument()` + 事务内，UNDO 由 CAD 自动按命令分组。

### 7.3 三个原子能力（分层，避免重复实现）

```csharp
// 1) 归层执行器：唯一的实际改层实现
public static class LayerAssignmentService
{
    public sealed class Outcome { public int Moved, AlreadyOnLayer, Locked, Failed; }
    public static Outcome MoveToLayer(Document doc, Transaction tr, ObjectId[] ids,
        ObjectId targetLayer, bool setByLayer, bool includeBlockAttributes);
}

// 2) 图层命令登记表：每个图层可有自己的命令（新增，替代散落的 FeatureRegistry 注册）
public sealed class LayerCommandRegistration
{
    public string LayerName;      // 目标图层
    public string Command;        // 内部命令，如 WLLAYER_ARCH_OUTLINE
    public string DefaultShortcut;// 默认快捷键，如 GC
    public bool Enabled = true;   // 是否为其生成快捷键/按钮
}
public static class LayerCommandRegistry
{
    public static IReadOnlyList<LayerCommandRegistration> All { get; }
    public static LayerCommandRegistration Ensure(string layerName); // 幂等，返回已有或新建
    public static void SetShortcut(string layerName, string shortcut); // 唯一写入入口
}
```

```csharp
// 3) 统一控制：FeatureRegistry 的图层命令来自 LayerCommandRegistry，
//    而不是手工维护两份
public static IReadOnlyList<FeatureDefinition> All
{
    get
    {
        var items = Items.ToList();
        foreach (var layer in LayerCommandRegistry.All.Where(x => x.Enabled))
            items.Add(ToFeature(layer));   // 动态合成，带 Group="图层工具"
        return items;
    }
}
```

这样"统一界面控制"是**结构保证**的：Ribbon、经典菜单、快捷键设置页
读的都是 `FeatureRegistry.All`，图层命令一旦登记就自动出现在三处，
不存在"两个界面各写一份、然后不同步"的可能。

### 7.4 两个入口，一份存储

| 入口 | 行为 |
|---|---|
| **图层归层对话框**（主命令，默认 `GL`） | 列出图层表（**按系统标签分组/序号**），选目标图层；勾选"颜色/线型/线宽随层""同时处理块属性""记住上次选择"；执行前预览将影响的对象数。对话框内每个图层行右侧直接给出**该图层的快捷键输入框**，就地设置。 |
| **每图层独立命令**（如 `GC`、`TZ`） | 由 `LayerCommandRegistry` 登记，默认快捷键可直接使用；**语义 = 用该图层预选目标执行同一套归层流程**，而不是另写一套逻辑。 |

两者共用 `LayerAssignmentService`，因此行为一致；
共用 `LayerCommandRegistry`，因此**不是一个把另一个盖掉**。

**分叉防护**：所有快捷键改动都经 `ShortcutSettingsService`
（`Load`/`Save` 已按 `FeatureRegistry` 全量校验唯一性与格式），
`LayerCommandRegistry.SetShortcut` 只是它的写入口，
**不允许任何界面直接写 `shortcuts.ini`**。若将来两层登记不一致，
`ShortcutSettingsService.Save` 的唯一性校验会直接报错，而不是静默生效一半。

### 9.3 既存缺陷（与本方案无关，先记录后修）

**楼梯 `WL.Stair.Cad2024` 无法编译。**

原因：`WL.Stair.Cad2024.csproj` 只 include 了

### 9.5 发布脚本的已知环境前提：`dist` 不能被占用

若 AutoCAD 从发布目录启动了插件（例如直接从
`dist\WanLuoArchitectureTools\` 加载，或运行过该目录下的启动器），
`acad.exe` 会**持有 `CadApi\Rxx\BatchPdfPublisher.dll` 的句柄**，
`Build-Release.ps1` 清理旧输出时会失败：

```
Remove-Item: ...\dist\WanLuoArchitectureTools\CadApi\R24\BatchPdfPublisher.dll
Access to the path ... is denied.
```

本次实测的特征很明确：`acad.exe` 于 15:12:18 启动，该 DLL 的
`LastAccessTime` 为 15:12:39，且无法以 `FileShare.None` 独占打开
（报 "being used by another process"）。

**这不是代码缺陷，而是运行前提**：跑发布前必须关闭 AutoCAD
（以及 `docs/BUILD_AND_INSTALL.md` 第 5 节"关闭全部 AutoCAD/天正进程"的同一要求）。
诊断顺序建议：

1. `Get-Process acad` 是否有实例；
2. 目标 DLL 能否以 `FileShare.None` 打开；
3. 排除残留的 `MSBuild` / `VBCSCompiler` 节点（`/m` 构建会留下工作节点，
   同样可能持锁；本次一度误判为节点持锁，结束节点后仍失败，才定位到 `acad`）。

**为什么不用反射调主插件**：反射要求主插件已加载到同一 AppDomain，
而楼梯可以在没有主插件时单独使用。直接读文件更可靠，且两侧**共用同一个用户数据根目录**
（`UserDataPaths.RootDirectory` 与 `WanluoDataPaths.Root` 都基于
`%APPDATA%\WanluoArchitectureTools\用户配置文件` 并都支持环境变量覆盖），已验证一致。

**失败即回退**：读不到文件、格式不认识、某项缺失，一律用内置常量——
行为与改造前完全一致，不会因为标准不可用导致楼梯出不了图。这正是
§4.2 选 A 的理由："失败时天然回退，行为不会更差"。

**同时识别两种配置格式**：主插件当前写 `LayerItem.N.Key` + `.Name` 与
`Text.N.Key` + `.Name`，旧配置是 `Layer.<Key>.Name` / `Text.<Key>.Name`。
两种都能解析，避免老用户标准读不到。

**一个已知取舍（需要知晓）**：这些字段是 `static readonly`，在类型初始化时解析一次。
用户在 BZS 里改完图层名后，需**重载插件或重启 CAD** 才对楼梯生效
（主插件自身的图层名读取是每次 `LoadProfile()`，实时生效）。
若要做到实时，需把字段改为属性、每次访问都读文件——会带来每根线条一次文件读取的开销，

**测试计数**：楼梯测试套件从 87 项增至 **92 项**（新增 5 项桥接测试方法、6 条 PASS）。
测试通过 `WANLUO_DRAFTING_STANDARD_DIR` 覆盖变量指向临时目录，不触碰用户真实配置。

**仍未走标准的两处（有意保留）**：
`WL_楼梯_临时裁切`（内部临时图层，不属用户可见标准）、
`Commands.cs:406` 的 `WL-图框`（楼梯命令建图框，与主插件 `Frame` 键同名，
应由主插件负责；楼梯这处是独立回退路径，暂不动）。

**发布验证抓出的一个漏项（值得记下）**：新增 `DraftingStandardBridge.cs` 后，
我只给引用它的 `Cad2022`/`Cad2024` 工程加了 `<Compile Include>`，
漏了 **`WL.Stair.Cad2026`**——它同样 link 了 `Cad2022/CadLineRenderer.cs`
（`WL.Stair.Cad2026.csproj:35`），却不会出现在任何 R24 构建里。
单独编译 Cad2022/Cad2024 全部通过，**只有完整发布脚本会编 R25 楼梯**才暴露：

```

```

教训：`StairDetail` 的四个工程（2022/2024/2026/Tests）都按文件逐个 link 共享源码，
